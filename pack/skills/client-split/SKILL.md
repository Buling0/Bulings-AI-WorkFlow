# 前端分离

输入一份策划案，输出一份只含客户端开发内容的需求文档。不写玩法代码，不建 `tasks.json`，不改策划案原文。

`.bulings/workflow.yaml` 的 `mode` 为 `indie` 时停止。输出路径默认 `Docs/AI/ClientSpecs/{feature}.md`（配置项 `clientSplit.path`），提示里给了路径以提示为准。

## 怎么分

逐条读策划案，每条需求归入下面之一：

- **客户端**：界面与布局、交互与操作反馈、动画与特效、音效、表现层状态、本地输入处理、对服务端数据的展示与请求发起、本地缓存、客户端侧的数值/规则演算（策划案明说由客户端算的）。
- **服务端**：权威数值与结算、数据存储、校验与防作弊、跨玩家逻辑、定时与排行。
- **配置/数据**：配表字段和数值。客户端要读的字段记进「依赖的配置」，不展开表本身。
- **待确认**：策划案没写清归属、或客户端/服务端说法冲突的条目。**不要自行归入客户端。**

一条需求同时涉及两端时拆开：客户端只留自己那一半，另一半写进「服务端依赖」。

## 客户端需求文档结构

1. **范围**：一两句话说明本文覆盖策划案的哪些部分，不含什么。
2. **客户端需求清单**：每条带编号 `C1、C2…`，写清行为、触发条件、期望表现；每条标注策划案出处（章节或原文片段）。
3. **服务端依赖**：客户端需要的接口/协议/字段，写“需要什么数据、何时请求”，没有定义的标明“协议未定”。
4. **依赖的配置**：客户端读取的配表与字段。
5. **涉及的预制体/界面**：策划案点名的，以及工程里能确认存在的相关预制体路径。读预制体前先看 `.cursor/skills/work-feature/prefab-reading.md`。
6. **待确认**：归属不明的条目和每条的疑问。
7. **已排除**：明确属于服务端或配置、未纳入的条目（一行一条，注明去向），方便核对没有漏项。

## 要求

- 不脑补：策划案没写的行为不要补，写进待确认。
- 不丢项：策划案每个需求点必须出现在清单、已排除或待确认之一。写完自查一遍。
- 项目约束里的目录、UI 框架等只用于定位预制体和命名，不写实现方案。
- 不创建 git commit，不改 `.meta` 的 guid。

## 衔接

文档写完后，开发走工作模式：把它当作策划案传入 `bulings run --design <客户端需求文档> --prefab ...`，或在 Cursor 里直接引用它让 `work-feature` 分析。
