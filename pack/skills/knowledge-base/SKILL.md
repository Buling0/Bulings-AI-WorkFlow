# AI 知识库维护

知识库是给后续 Agent 读的工程说明，帮它们少扫代码、少猜约定。它**依据代码**写，不依据愿望写。只写 Markdown，不改玩法代码。

`.bulings/workflow.yaml` 的 `mode` 为 `indie` 时停止。知识库根目录默认 `Docs/AI/Knowledge`（配置项 `knowledge.root`），提示里给了路径以提示为准。

## 目录结构

```
<root>/
  MAP.md              地图：入口。work-feature 分析前先读它
  conventions.md      约定：命名空间、目录、asmdef、命名、UI 绑定方式、资源规则
  architecture.md     架构：分层、模块依赖、启动与数据流、事件/消息机制
  modules/<模块>.md   模块页：一个模块一页
```

模板见 [map-template.md](map-template.md) 和 [module-template.md](module-template.md)。

## 写作规则

1. **事实要有出处**：每条结论带代码路径（可到类名），读不到证据的写进「待核实」，不要补全。
2. **只写稳定的东西**：目录职责、模块边界、入口类型、约定。不抄方法体、不写易变的行数/字段清单。
3. **和配置对齐**：`workflow.yaml` 的 `project` 已配置的项（代码目录、命名空间、UI 框架等）直接引用，不重复推断；冲突时以配置为准并在「待核实」里记一笔。
4. **单页要短**：模块页超过一屏就拆；地图只放链接和一行说明。
5. 每页文件头写 `最后核对：<日期>` 和 `依据：<代码目录>`，供检查时判断是否过期。
6. 不创建 git commit，不改 `.meta` 的 guid，不改 `protectedPaths` 里的路径。

## 动作

### init：首次建立

1. 读 `workflow.yaml`，找到代码根目录；没配置就看 `Assets/` 下的 asmdef 和脚本目录。
2. 先写 `conventions.md` 和 `architecture.md`，再按模块（优先以 asmdef 或顶层脚本目录为单位）写模块页，最后写 `MAP.md`。
3. 已存在的页面不覆盖整页：保留其中人工写的内容，只补缺的部分，改动处在页尾「变更记录」记一行。

### update：功能做完后维护

提示会给出功能名和任务文件 `tasks.json`；改动范围以任务里的 `files` 和 git 工作区改动为准。

1. 只看受影响的模块：改了哪些目录/类型，就核对对应模块页。
2. 新增模块 → 新建模块页并加进 `MAP.md`；删除或重命名 → 同步改页面和地图链接。
3. 约定或架构被本次改动改变（新增事件机制、新的 UI 绑定方式等）→ 更新 `conventions.md` / `architecture.md`。
4. 本次改动和策划不一致、或和知识库原有描述冲突的地方，以代码为准，在页尾「变更记录」写明原因。
5. 没有需要改的就不改，明确说“无需更新”。不要为了有产出而改页面。

### check：核对

不改知识库页面，只输出报告（写到 `<root>/CHECK.md`，覆盖旧报告）：

- **过期**：页面提到的路径/类型在代码里已不存在。
- **缺失**：代码里有的模块（asmdef 或顶层脚本目录）地图里没有。
- **冲突**：页面描述与代码行为不符。
- **孤儿**：模块页没有被 `MAP.md` 链接。

每条给出页面、证据路径和建议动作。修复由用户决定后再用 `update` 做。
