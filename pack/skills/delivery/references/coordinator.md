# 协调者规则

协调者待在用户对话里，维护交付档案、判断当前阶段、在材料齐全后交接下游。本规则只描述六段职责与写作边界；阶段目录与命令以 Bulings 交付档案为准。

## 六段职责

| 阶段 | 目录 | 职责 |
| --- | --- | --- |
| 需求 | `01-requirements` | 用户要确认的目标、范围、验收和边界。 |
| 调查 | `02-investigation` | 仓库和环境能证明的事实与未知。 |
| 设计 | `03-design` | 基于需求和证据做出的方案、职责和行为。 |
| 计划 | `04-plan` | 可分别验收的结果、顺序、依赖和回滚。 |
| 实施 | `05-implementation` | 工作区里的实际变化和执行结果。 |
| 验证 | `06-validation` | 实际证据、结论、未验证边界和残留风险。 |

## 写作与边界

- 事实类型不能互相冒充：需求里不写实现细节，调查里不做设计决定，设计里不冒充已验证结论，验证里不替用户确认目标。
- 内容简单时只维护该阶段总览（`README.md`）；不要为了形式拆很多专题文件。
- 交付档案不是长期知识库。用户没指定目标路径时，不要另写项目文档或把档案复制到 `Docs/` 等目录。
- 术语表在 `01-requirements/terminology.md`，与需求总览分开维护；需求正文引用术语，不在总览里重复定义。

## 当前阶段（本版本）

机器尚未写入阶段字段。以六份阶段总览中**第一份**正文仍为「待填写」的阶段为当前阶段，顺序为：需求 → 调查 → 设计 → 计划 → 实施 → 验证。若六份都已写过实质内容，则停在验证，并说明整体验收与封存相关命令可能尚未安装。

## 冷读

需要冷读时，运行 `bulings delivery cold-read-prompt`，在**新的 Agent 对话**里只使用命令返回的 `prompt`；不要把当前对话历史贴进提示，也不要在本对话里冒充冷读结论。

## 协调者不做的事

- 不创建 git commit，不改 `.meta` 的 guid，不启动 Unity 批处理。
- 不修改 `.bulings/workflow.yaml` 里 `protectedPaths` 所列路径。
- 实施切片与租约在本版本之后才有；本阶段只写文档与查状态，不抢工作区写入。
