# 需求阶段规则

协调者维护 `01-requirements/README.md`（需求总览）与 `01-requirements/terminology.md`（术语表）。本规则只约束需求总览正文结构与人机确认边界。

## 正文结构

YAML 前置之后，需求总览必须按以下结构维护：

```markdown
# 需求

## 当前决定

这一节写本次需要人决定的事项。没有待决定项时写「无」。

## 场景

### <场景名>

- 主体：
- 初始条件：
- 操作：
- 可观察结果：
- 来源：<策划或资料的相对路径>#<可复核定位>

## 非目标
```

- 至少有一个 `###` 场景；场景名在本交付项内唯一。
- 「主体」「初始条件」「操作」「可观察结果」「来源」五项均须非空。
- 不要按控件、Prefab 或源文件拆场景；取消与失败写在同一场景的「可观察结果」里。
- 「来源」在相对路径指向的文件存在时视为有效；尚未有资料时可写 `待提供：<缺什么>`，但**不能**在该状态下批准需求。

## 协调者怎么写

- 按**可单独判断的业务场景**写「场景」，不写实现步骤或任务列表。
- 实现细节未知时写入 `02-investigation`，不要求用户先拆开发任务。
- 交给用户确认的，只是会改变**目标、外部行为、验收或范围**的分叉；其余推断留在调查或设计。
- 术语定义放在术语表，需求总览只引用，不重复长定义。

## 冷读与批准

- 需要第三方视角核对材料时，用 `bulings delivery cold-read-prompt` 生成交接提示，在**新的 Agent 对话**中执行；不要把当前协调者对话历史贴进提示。
- 用户用真实回复确认后，用 `bulings delivery approve-requirements` 登记 `--user-confirmation` 与 `--locator`；批准绑定当时的需求与术语指纹，之后语义变化会使批准失效。
