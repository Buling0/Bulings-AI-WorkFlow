# 工作模式功能开发

用于公司 Unity 工程。输入是一份策划案和相关预制体。先列出可逐项完成的任务，再写代码，并按配置决定要不要留下两份中文文档。

`.bulings/workflow.yaml` 的 `mode` 为 `indie` 时不要在这里做，改用 `indie-feature` Skill（独游模式先立框架，再按纵向切片做功能）。

## 配置

读取工程根目录的 `.bulings/workflow.yaml`。没有文件时：`mode` 为 `work`，开发说明写到 `Docs/AI/DevSpecs/{feature}.md`，功能说明写到 `Docs/AI/Features/{feature}.md`，两份都生成。

提示里如果写了文档路径或开关，以提示为准。

`project` 里的空字符串和空数组表示未配置。未配置的项从工程里看目录、命名空间和 asmdef，写进开发说明的「推断的项目约定」。不要把未配置项写成必须遵守的规范。

`protectedPaths` 里的文件不要改。不要创建 git commit。不要改 `.meta` 的 guid。不要启动 Unity 批处理编译。

## Unity MCP

配置了 Unity MCP 并且连得上时，可以用它读编辑器状态、刷新编译、读控制台、在编辑器里绑定预制体。用法和边界见 [unity-mcp.md](unity-mcp.md)。连不上就如实说，不要假装验证过。

## 只做客户端

策划案同时含客户端和服务端内容时，先用 `client-split` Skill（命令行 `bulings split`）分离出客户端需求文档，再把它当策划案来分析。

## 知识库

项目约束里如果给出了知识库地图，分析前先读它，再读它指向的约定和架构。做具体功能时，按地图打开对应页面，并先在地图列出的代码目录里找。知识库和代码不一致时以代码为准，把差异写进开发说明。知识库的建立和维护见 `knowledge-base` Skill（命令行 `bulings kb`）。

## 听提示选阶段

- 点名分析，或只要开发说明：只做分析。
- 点名任务编号：只实现该任务。
- 点名功能说明或维护文档：只写功能说明。
- 都没点名：按顺序自己做完，一次只实现一个任务。做完一项并更新状态后，再取下一项。

命令行每一轮都会点名阶段。不要提前做下一阶段。

## 缺失分析（分析阶段的第一步）

读完策划案和预制体后，**先找这次做不下去或做不完整的地方**，再拆任务。不要一边写代码一边发现缺东西。

### 分四类找

| 类别 | 查什么 | 缺的时候记什么 |
| --- | --- | --- |
| 策划 | 策划案里的规则、数值、状态流转、触发条件、边界情况；玩法要用的配置表 / 数据表条目、开关、文案 | 缺哪条规则或哪份配置、配置里缺哪个字段或哪几行、建议的默认值、要谁补 |
| 后端 | 这次要用的协议号是否存在、协议字段和策划要的数据是否一一对得上、是否有重复或占位协议、需求里有没有本应给却没给的协议 | 还差哪个协议、要哪些字段和类型、按哪份协议文档、要谁提 |
| 美术 | 预制体是否真的能承接需求：缺节点、缺组件、结构和策划描述不符、缺 UI 图或特效、绑定关系缺失 | 哪个预制体的哪个节点、和策划哪一条不符、要新增/改成什么样 |
| 前端 | 显示逻辑没说清的地方：什么时候显示、优先级、层级、互斥、刷新时机、动效和时长、空态和异常态 | 哪条显示逻辑不明确、现在有两种以上合理解释、需要策划确认哪一种 |

只为这次功能相关的部分找，不要把整个工程扫一遍。读不到证据就记「缺」，不要自己补。

### 分阻断与非阻断

- **阻断**：这一块不给就没法按策划实现，或者实现出来一定和策划不一致。典型是规则没定、协议号没有、预制体结构对不上、显示逻辑有两种以上合理解释。
- **非阻断**：可以先用保守做法落地，后面拿到更完整的资料再补。典型是文本和图标占位、不影响流程的表现细节、后续会补的数据行。

拿不准的按阻断处理——先问，比返工便宜。

### 怎么写进产物

- 阻断项：对应任务 `status` 写 `blocked`，`blockedReason` 以类别开头，写清「缺什么 + 要谁补」。例如 `后端：缺 10023 协议（奖励领取），需要协议文档和字段定义`。没有对应任务的，单独建一项只有阻塞、没有实现动作的任务，别把它硬塞进别的任务。
- 非阻断项：对应任务照常 `pending`，在开发说明的「缺失与待补齐」里记一行，写清缺什么、这次先用什么代替。
- 两类都按「策划 / 后端 / 美术 / 前端」四段整理，同一类里的条目按对流程的影响从大到小排。

### 汇报与等待

分析结束时，按四类把阻断项汇报给用户，写清缺什么、要谁补，然后**停下来等补齐**。不要绕开它去做后面的任务，也不要用占位实现冒充完成。补齐后用户会重新发起分析或点名任务：这时只更新受影响的条目和任务，已经 `done` 的不要重做。

非阻断项不打断流程：照常实现，等流程结束后在和用户的回复里汇总一次（功能说明开启时也写进功能说明），不要每做一项就报一遍。

## 预制体绑定

节点和组件的引用**优先在预制体内用脚本绑定**，不要用运行时按名字查找兜底。

按这个顺序选方案：

1. 预制体已经把目标引用好了（序列化字段有值）——直接用。
2. 工程里已有绑定脚本或生成器（`project.ui.binding` 写了 `partial class` 生成、代码生成器等）——按工程既有做法，在预制体内生成绑定代码并绑上引用。
3. Unity MCP 可用——用 MCP 在预制体上生成绑定代码、绑定序列化字段、保存预制体。

**不允许**把 `transform.Find("X")`、`GameObject.Find`、按节点名 `GetComponent` 当成主方案。只有两种情况才允许，并且必须写进「已知限制」：

- 这个预制体或工程本来就用按名字绑定（`project.ui.binding` / `project.ui.notes` 里写了）；
- 用户明确要求。

做不到就地绑定时（MCP 连不上、预制体是第三方/只读、工程没有绑定生成器），**不要自己按名字找兜底**：在开发说明的「预制体绑定」一节列出「哪个预制体、哪个节点、要绑什么类型、为什么不能就地生成」，并在回复里直接告诉用户要补哪几个预制体。

## 流程图门禁

工作模式默认在写代码前先出一张流程图，用户确认后才进入实现。

分析阶段除了 `tasks.json`，还要写 `.bulings/runs/<slug>/flow.md`（提示词里会给路径），内容至少四块：

- 「页面与入口」：有哪些页面/面板，从哪进；
- 「页面交互流程」：用户操作 → 界面反应 → 状态变化；
- 「数据流向」：数据从哪来、经过谁、落到哪、谁刷新界面；
- 一张 mermaid 图（`flowchart` 或 `sequenceDiagram`）。

最后一行写 `<!-- flow-status: draft -->`，**不要自己改成 confirmed**——确认由用户跑 `bulings resume --confirm-flow` 完成。写完流程图就停，不要提前写代码；工作流会在实现前检查这张图。

实现阶段按这张图写，不要偏离页面交互和数据流向；确认后发现图有问题，改图并说明，不要闷头按旧图写完。

## 分析

不要写玩法代码。

1. 读策划案。如果项目约束给出了知识库地图，先按「知识库」一节读完再拆任务。
2. 读预制体前先看 [prefab-reading.md](prefab-reading.md)。分析提示里给出的预制体。策划案点名、且工程里真实存在的其他预制体可以一并看。
3. 先按「缺失分析」找出阻断项和非阻断项，再拆任务。策划和预制体对不上时不要脑补，标 `blocked` 并写 `blockedReason`。
4. 按依赖排序。一项任务只做一块能看完的改动：一个脚本、一处预制体绑定，或一个数据类。
5. 无论开不开发说明，都写 `.bulings/runs/<slug>/tasks.json`。提示里有路径就用那个路径。

`tasks.json`：

```json
{
  "feature": "功能名",
  "designDoc": "策划案相对工程的路径",
  "prefabs": ["预制体相对工程的路径"],
  "tasks": [
    {
      "id": "T1",
      "title": "一句话",
      "goal": "这一项完成什么",
      "dependsOn": [],
      "files": ["Assets/Scripts/Example.cs"],
      "prefabNodes": ["Canvas/Panel"],
      "acceptance": ["可核对的完成标准"],
      "status": "pending"
    }
  ]
}
```

`status` 只能是 `pending`、`in_progress`、`done`、`blocked`。`id` 不要重复。阻塞时增加 `blockedReason`，并在开头写缺失类别。

开发说明开启时，按 [dev-spec-template.md](dev-spec-template.md) 写到指定路径。任务用 `- [ ]`，并写上编号、目标、依赖、脚本或节点、完成标准、状态；「缺失与待补齐」一节按四类写这次的阻断项和非阻断项。

分析阶段出现 `blocked` 任务时，流程停在这里，等用户补齐缺失内容后再继续。不要在阻断项还挂着的时候往下写代码。

开发说明里还要写两块：每个预制体的「预制体绑定」方案（见上一节）和「待用户补绑定的预制体」；流程图开启时，把流程图路径和「页面 / 数据流」摘要记进开发说明，图本身写到 `.bulings/runs/<slug>/flow.md`。

## 实现一个任务

只做这一项要动的文件。

1. 在 `tasks.json` 里把该任务标成 `in_progress`。开发说明里把状态改成 `in_progress`。
2. 打开用户确认过的流程图（存在时），按图实现页面交互和数据流向；图和现实对不上就先把差异记下来，不要默默偏离。
3. 绑定节点引用按「预制体绑定」的顺序做：先看预制体已有引用，再按工程的绑定脚本/生成器，最后用 MCP 生成并绑定。不许用运行时按名字查找兜底；绑不了就标 `blocked` 并在「预制体绑定」里写清要用户补哪个预制体。
4. 实现中发现新的缺失：按「缺失分析」判断阻断与否。阻断就标 `blocked`，`blockedReason` 以类别开头写清缺什么，然后停止；非阻断就先用保守做法做完，记进「缺失与待补齐」。
5. 遇到 `protectedPaths`，或必须改 `.meta` guid 才能完成时，标 `blocked` 并写 `blockedReason`，然后停止。
6. 做完后把 `tasks.json` 标成 `done`。开发说明把 `- [ ]` 改成 `- [x]`，状态改成 `done`。
7. 做不到且不应该猜测时，标 `blocked`，复选框保持未勾，写上原因。

提示如果说明这是中断后的重做，或这项上次已阻塞：只修补这一项，不要重做已经 `done` 的任务。

本轮提示点了任务编号时，做完就停。没有点名阶段时，更新状态后再取下一项。

## 功能说明

只在功能说明开启、且任务全部是 `done` 时写。按 [feature-doc-template.md](feature-doc-template.md)，依据实际改过的代码。不要把任务清单再抄一遍。这一阶段不要再改玩法代码。

写完功能说明后，把这次的非阻断缺失按四类汇总一次告诉用户：缺什么、现在用什么代替、后续什么时候要补。功能说明开启时也写进「未补齐的非阻断项」。

提示点名要维护知识库时，写完功能说明后按 `knowledge-base` Skill 的 update 动作只更新受影响的页面。
