# 独游模式说明

`mode: indie` 是给个人 / 小团队 Unity 小型游戏用的流程。它和工作模式共用 `bulings run` / `resume`、`tasks.json`、`state.json` 和退出码，差别只有两条：

1. **先立框架，再做功能。** 第一次跑功能之前先落一套能承接新玩法的骨架，把扩展点登记下来；后面每个切片都挂在扩展点上。
2. **按纵向切片推进。** 一项任务 = 一条能自己验收完的能力（数据、逻辑、表现、接线），不按技术层横切。

为什么这么设计：小游戏的功能数量少、迭代快，最贵的错误不是"某个功能写错"，而是"每个功能各造一套事件/配置/存档，第二个功能就接不进去"。框架先行 + 挂载点校验，把可扩展性变成流程里的一道确定性检查，而不是一句口号。

---

## 一、流程

```text
run
 ├─ 框架阶段（没有可用框架时才跑）
 │   读策划案与工程现状 → 选范式 → 目录/asmdef → 核心系统落地
 │   → 写 .bulings/indie/framework.json（Agent 写，工作流校验）
 │   → 写 Docs/AI/Frameworks/<game>.md
 ├─ 分析：按纵向切片拆任务，每项写 framework 挂载点
 │   → 校验挂载点，不通过就停在这里
 ├─ 实现：一轮一项切片，复用扩展点，需要时追加登记
 └─ 功能说明：写清挂载点、新增扩展点、下一个功能从哪接
```

阶段状态记在 `.bulings/runs/<功能名>/state.json` 的 `phase`：`framework` → `analyze` → `implement` → `document` → `done`。

### 框架阶段什么时候跑

`framework.json` 不存在、不合法，或 `status` 仍是 `draft` 时跑。已经有可用框架时直接进分析，只对"登记过但磁盘上找不到"的路径打一行警告，不阻塞。

中断在半路也能接着做：`framework.json` 留着 `status: draft`，`resume` 会把草稿摘要交给 Agent，只补没做完的部分。

框架阶段的产物不合法（`status` 还是 `draft`、`systems` 为空、字段缺失）时退出码是 `2`，**不会**进入功能代码。

### 框架阶段做什么

先读 `.cursor/skills/indie-feature/frameworks.md` 选型，默认是零外部依赖的轻量自建基线：启动与生命周期、服务注册、事件、状态机、SO 配置、存档；对象池、音频、输入、场景加载、UI 接入按需再加。

工程里已有范式（`project.architecture`、`project.ui`、已有代码）时服从工程，不为了"规范"重写已有代码。`indie.framework.paradigm` 填了就按它做。

框架阶段**不写玩法功能**。留空壳（只有类名没有职责）不算完成——宁可 `status: pending`，也不要挂空壳。

## 二、`framework.json`

路径由 `indie.framework.plan` 决定，默认 `.bulings/indie/framework.json`。工程级，不是每个功能一份。

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `game` | 是 | 游戏标识，一般用工程目录名 |
| `paradigm` | 是 | 采用的范式，一句话 |
| `root` | 是 | 代码根目录，相对工程根 |
| `assemblies` | 否 | 程序集名 |
| `systems[]` | 是 | 至少一项；`id`（唯一、切片引用它）、`title`、`paths`、`status`（`pending`/`done`）、`notes` |
| `extensionPoints[]` | 否 | `name`（切片引用它）、`howTo`、`path` |
| `conventions` | 否 | 目录、命名、依赖方向的约定 |
| `status` | 是 | `draft` 或 `done`；`done` 时至少一个系统是 `done` |

完整示例和校验规则见 `.cursor/skills/indie-feature/framework-template.md`。

**为什么扩展点要单独登记**：切片只能挂在这里登记过的系统或扩展点上，框架里没有的必须先写 `new:` 再补登记。这样"新加的东西"一定会落回框架，不会散落在各功能里。

---

## 三、挂载点校验

`tasks.json` 里每项任务的 `framework` 字段：

- 取值来自 `systems[].id` 或 `extensionPoints[].name`；
- 框架里还没有的，写 `"new: 一句话说明"`，实现阶段再补登记；
- 空数组、未知名字、`new:` 后面没说明，都会在**写代码之前**停下（退出码 `2`，`phase` 回到 `analyze`），并列出可用挂载点。

`framework.json` 不合法或读不到时，只报一条"框架基线缺失"，提示先补框架或确认后加 `--no-framework`。

### 关掉框架阶段

`--no-framework` 或 `indie.framework.enabled: false` 时不跑框架阶段，切片只需写清 `framework`（允许 `new: <说明>`），不校验框架内容。适合已经有自己一套架构的工程——这时候把 `project.architecture` 填清楚比让 Agent 重搭更有用。

## 四、和工作模式、交付流的边界

| | 工作模式 `mode: work` | 独游模式 `mode: indie` | 交付流 `bulings delivery` |
| --- | --- | --- | --- |
| 面向 | 公司工程，有服务端、要接预制体 | 个人 / 小团队小游戏 | 跨多轮、要独立评审的长任务 |
| 输入 | 策划案 + 预制体（必填） | 策划案（预制体可空） | 需求来源文件 |
| 骨架 | 服从工程既有框架 | 先立框架，再挂切片 | 按交付档案分阶段 |
| 评审 | 无独立评审 | 无独立评审，有挂载点校验 | 独立评审 + 验证 + 封存 |
| 文档 | 开发说明 + 功能说明 | 开发说明 + 框架文档 + 功能说明 | 六阶段交付档案 |

独游模式下 `bulings split` 会拒绝执行（默认没有服务端）；需要分离时把 `mode` 临时改成 `work` 跑一次再改回来。`bulings kb` 两种模式都能用。

## 五、产物位置

| 产物 | 位置 |
| --- | --- |
| 框架清单 | `.bulings/indie/framework.json` |
| 框架文档 | `Docs/AI/Frameworks/<工程目录名>.md` |
| 任务列表（含切片与挂载点） | `.bulings/runs/<功能名>/tasks.json` |
| 运行状态 | `.bulings/runs/<功能名>/state.json` |
| 开发说明 | `Docs/AI/DevSpecs/<功能名>.md` |
| 功能说明 | `Docs/AI/Features/<功能名>.md` |

## 六、常见问题

| 现象 | 处理 |
| --- | --- |
| 退出码 2，提示框架不合法或还是 draft | 打开 `framework.json` 补齐 `systems`，全部可运行后把 `status` 改成 `done`，再 `bulings resume` |
| 提示切片没有挂在框架上 | 看报错里列的可用挂载点；确实要新增就写 `new: <说明>`，实现阶段它会补登记 |
| 提示框架基线缺失 | 先补框架阶段，或确认后加 `--no-framework` |
| 框架登记的文件找不到 | 只是警告。重构后路径变了就把 `framework.json` 里的 `paths` 更新掉 |
| 改回 `mode: work` 后 `resume` 报错 | 一次运行绑定建立时的模式。改回 `indie` 继续，或另开一次运行 |
| 想在已有框架的工程上直接用 | 把 `project.architecture` / `ui.*` 填清楚，再加 `--no-framework` |

## 七、验证状态

框架阶段、挂载点校验、模式切换和断点都有 pytest 覆盖（假 Agent 驱动，不联网）。**还没有用真实 Agent 端到端跑过**：首次在真机上使用，建议先拿一个只有核心循环的小工程试一次，确认它产出的框架清单和你的工程结构对得上，再放到正式项目里。
