# 独游模式需求补充

> 范围：只涉及 `workflow.yaml` 的 `mode: indie` 这条线（`bulings design`、`bulings run` / `resume` 的独游流程、`indie-design` / `indie-feature` 两个 Skill）。工作模式和交付流不动。
>
> 来源：对独游模式的代码走查，见已整理的分析。本文只收**要落地的部分**，并在第 7 节写明这次**不做**的部分和理由。

## 1. 背景

独游模式已经能跑通「一句话灵感 → 策划案迭代 → 框架 → 纵向切片 → 功能说明」，但走查发现两类问题：

1. **校验比它承载的东西松**：策划案可以「状态文件写得很漂亮、正文一个字没动」地推进；`--finish` 不要求四个维度确认；框架文档没人检查；切片粒度和依赖没有机械约束。
2. **缺少工程级视图**：多份策划案、多个 feature 的工程里，没有一条命令能回答「现在到哪了、卡在哪、下一步敲什么」。

这两类问题的共同后果是：状态看起来完成，实际是空壳；或者需要人去翻 `.bulings/` 才能知道下一步。

## 2. 目标

- 让「完成」在策划案、框架、切片三层都有可校验的标准，不再是提示词里的君子协定。
- 让约束违反（改了 `protectedPaths`、动了 `.meta`）至少被看见。
- 给独游工程一个总览入口，并把「下一步敲什么」直接印出来。
- 不改变现有流程形态：阶段顺序、产物位置、退出码语义都不动。

## 3. 非目标

- 不改工作模式（`work-feature`）和交付流（`bulings delivery`）。
- 不引入 git commit、不调用 Unity 批处理编译。
- 不改 `design.json` / `framework.json` / `tasks.json` 的既有必填字段。新增字段一律可选，旧文件照样能读。
- 不做真实 Agent 端到端验证（测试仍用假 Agent）。

## 4. 需求清单

编号约定：`D` 策划案迭代、`F` 框架、`T` 切片、`V` 改动审计、`R` 视图/工具、`P` 提示词。

### D1 每一轮的选择必须留痕

**现象**：`--note` 单独推进的一轮，如果 Agent 没往 `chosen` 里追加 `{round, ids: [], note}`，校验照样通过，开发者的决定在状态文件里丢失；`--decide` 只校验 id 在 `chosen` 的历史里，不要求记在本轮。

**要求**：

- 本轮若带了 `--decide` 或 `--note`，`chosen` 里必须有一条 `round == current.round` 的记录。
- 带 `--decide` 时，这一轮记录的 `ids` 必须**恰好**包含这些 id（缺了报错，多的不报）。
- 报错文案点明「这一轮的选择没有记进 chosen」并给出当前 `round`。

**验收**：`--note` 一轮但 Agent 没记 `chosen` → 退出码 `2`；正常记录 → `0`。

### D2 定稿要求四个维度都确认

**现象**：`--finish` 只检查 `status: done`、`options` 为空、正文非空。四个维度全是 `confirmed: false` 也能定稿。

**要求**：

- `--finish` 时 `dimensions` 四项必须都 `confirmed: true`。
- 确实要放行时给 `--force`，并在终端说明「绕过了维度确认」。
- 报错时列出还没确认的维度名称。

**验收**：未确认 → 退出 `2` 并列出维度；加 `--force` → `0`。

### D3 每一轮正文必须真的变厚

**现象**：轮次校验只看 `design.json`，第 1~N 轮从没检查过策划案正文。可以只更新状态文件、正文不动。

**要求**：

- 每轮开始前记下正文的 size + mtime；本轮结束后若正文未变化（size 和 mtime 都没变），打印明确警告：本轮正文没有更新。
- 这是**警告不阻断**：Agent 可能合法地只改了一处措辞，硬卡会误伤。
- 定稿轮保持现有硬校验（正文必须存在且非空）。

**验收**：正文不变时 stderr 出现该警告；正文变化时没有。

### D4 轮次提示

**现象**：`design.rounds`（建议轮次）只写进提示词，命令行从不提示；用户不知道什么时候该 `--finish`。

**要求**：

- 设计状态输出里加一行：`第 N 轮（建议 R 轮）`；`N >= R` 时提示「已到建议轮次，可以考虑 --finish」。
- 四个维度都确认、且这一轮没有新选项时，直接提示可以 `--finish`。

**验收**：`--decide` 推进到第 2 轮后，输出里有建议轮次；超过建议轮次时有收尾提示。

### F1 框架文档必须真的写出来

**现象**：`prepare()` 只校验 `framework.json`，`indie.framework.doc` 指定的框架文档从未被检查。提示词写「必须写入」，但没写也能进功能代码。

**要求**：

- 框架阶段通过后，检查框架文档存在、非空。
- 文档内容仍是模板骨架（含 `{game}`、`{游戏名}` 这类未替换占位符，或只有骨架标题没有正文）时，视为没写。
- 缺失时退出 `2`，提示补文档或把 `indie.framework.docEnabled` 设为 `false`。

**验收**：只有 `framework.json`、没有框架文档 → 退出 `2`；两份都有 → `0`。

### F2 `root` 参与漂移检测，路径必须是相对路径

**现象**：`framework_drift` 只查 `systems[].paths` 和 `extensionPoints[].path`，`root` 写成不存在的目录也能 `ready`；绝对路径也能混进去。

**要求**：

- `root` 和所有登记路径都进漂移检测。
- 解析时拒绝绝对路径（Windows 盘符、`/` 开头），报错说明「用相对工程根的路径」。

**验收**：`root` 不存在 → 漂移列表包含它；绝对路径 → 解析失败。

### F3 扩展点四类软校验

**现象**：`frameworks.md` 要求扩展点至少回答「新状态 / 新事件 / 新配置 / 新存档字段」，但 `extensionPoints: []` 也能 `status: done`。

**要求**：

- 框架阶段通过后，`extensionPoints` 为空时打印警告（不阻断）；不足四条时也只警告，提示缺哪几类（按 `howTo` 关键词粗匹配：状态、事件、配置、存档）。
- 理由：小项目可能只做得到两三样，硬卡会逼人凑数。

**验收**：空扩展点 → 有警告但仍 `0`。

### T1 独游模式的切片必须写 `slice`

**现象**：`slice` 是可选字段，`validate_indie_tasks` 只校验 `framework`。独游的核心承诺「一项任务 = 一条纵向切片」完全靠提示词。

**要求**：

- 独游模式下每项任务必须有非空 `slice`，缺失时在写代码前停下并列出任务 id。
- 工作模式不要求（`slice` 仍是可选）。

**验收**：独游任务缺 `slice` → 分析阶段退出 `2`；补上 → `0`。

### T2 依赖写错时报清楚

**现象**：`dependsOn` 指向不存在的 id、或几项互相依赖时，`select_next_task` 只返回 `waiting`，终端只说「依赖无法满足」。

**要求**：

- 校验时检查：`dependsOn` 引用的 id 必须存在；不许自依赖；不许成环。
- 成环或缺 id 都在**写代码前**报错（退出 `2`），列出具体任务和依赖。
- 运行期 `waiting` 的提示补上缺哪几个依赖。

**验收**：缺 id / 成环 → 分析阶段退出 `2`；正常依赖 → `0`。

### V1 改动范围审计

**现象**：提示词反复要求「不改 `protectedPaths`、不动 `.meta`」，但没有任何检查。

**要求**：

- 新增 `bulings audit --project <工程>`：用 `git status --porcelain` 取工作区改动，报告三类风险：
  1. 改动命中 `protectedPaths`（错误级）；
  2. 改动了 `.meta` 文件（警告级，可能是 Unity 自动改的）；
  3. 改动落在 `project.codeRoots` 之外（提示级，只在配置了 codeRoots 时）。
- 不是 git 仓库时明确说明「无法审计」，退出码 `0`（没东西可查，不算失败）。
- 每个阶段（框架 / 分析 / 功能说明）结束后自动跑一次**只报错误级**的检查并打到 stderr，不改变退出码，避免误伤已有改动。

**验收**：改了 `protectedPaths` 里的文件 → `audit` 退出 `1` 并点名文件；干净工作区 → `0`。

### R1 `bulings status`：一屏看完工程进展

**要求**：

- 新增 `bulings status --project <工程> [--json]`，输出：
  - 模式与工程名；
  - 所有策划案：轮次 / 是否定稿 / 维度确认数 / 正文路径；
  - 框架：是否就绪、系统数、pending 数、扩展点数、漂移列表（最多列 5 条）；
  - 所有运行：feature、phase、任务完成数 / 总数、阻断项（id + `blockedReason`）；
  - 下一步建议命令（按当前状态给一条，最多两条）。
- `--json` 输出同一份数据的 JSON，方便别的工具消费。
- 没有任何产物时说明「还没有策划案/框架/运行」，退出码 `0`。

**验收**：构造一个含策划案 + 框架 + 一个被阻断的运行，`status` 能同时列出三块信息；`--json` 可被 `json.loads` 解析。

### R2 `bulings design --history`

**要求**：

- 每轮结束把当时的 `design.json` 快照到 `.bulings/design/<slug>/rounds/<round>.json`。
- `bulings design --project <工程> --name <slug> --history` 列出每轮的 round、stage、status、本轮选项 id、本轮选择；某轮没有快照就标「无快照」。
- `--history` 只读，不启动 Agent。

**验收**：跑两轮后 `--history` 至少列出两个轮次；`--json` 可解析。

### R3 `bulings doctor`：环境自检

**要求**：

- 新增 `bulings doctor --project <工程>`，逐项打印 `[OK] / [WARN] / [FAIL]`：
  - 是不是 Unity 工程（`Assets` + `ProjectSettings`）；
  - `workflow.yaml` 能否解析、mode 是 work 还是 indie；
  - 当前模式的 Skill 是否已安装（`.cursor/skills/<mode>/SKILL.md`）；
  - `CURSOR_API_KEY` 是否存在；
  - Unity MCP：配置是否启用、URL 是否可达（只做 TCP 连接，1 秒超时，失败只 WARN）；
  - 独游模式额外检查：框架就绪、框架文档存在、`indie.design.path` 目录可写。
- 有任一 `FAIL` 时退出 `1`，只有 WARN/OK 时退出 `0`。

**验收**：非 Unity 工程 → 有 FAIL 且退出 `1`；正常工程 → 退出 `0`。

### P1 提示词精简

**要求**：

- 实现阶段不再注入完整框架摘要，只注入「本任务引用的挂载点 + 框架约定 + 框架文件路径」；分析阶段保留完整摘要（它要选挂载点）。
- `_next_design_stage` 遇到已定稿的策划案时返回 `done` 而不是 `polish`，避免定稿后提示词又说「这一轮推进数值与里程碑」。
- 缺失分析的判定规则仍留在提示词里（Skill 加载失败时兜底），但压缩成一行指向 Skill。

**验收**：实现阶段提示词里不再出现 `systems` 全表；已定稿时 `_next_design_stage` 返回 `done`。

## 5. 数据结构与配置

### design.json（新增可选字段）

无。D1~D4、R2 只改校验和快照，不改 schema。

### 快照文件

```text
.bulings/design/<slug>/rounds/<round>.json    # 每轮 design.json 的原样副本
```

### framework.json

无新增字段。F1~F3 只改校验（路径必须相对、框架文档、扩展点软校验）。

### workflow.yaml（无新增必填项）

无新增配置。F1 提到 `indie.framework.docEnabled` 作为放行开关，是可选的扩展：`true`（默认，要求框架文档）或 `false`（不要求）。

## 6. 兼容性与测试

- 所有新校验都排在「写代码之前」，退出码统一 `2`；不改变 `0/1/2` 的既有语义。
- 旧工程：`framework.json` 里若有绝对路径会从「能跑」变成「解析失败」，属于**有意的不兼容**，在升级说明里写明。
- 测试：
  - `test_gdd.py`：D1（note 未记录、decide 记错轮次）、D2（未确认/`--force`）。
  - `test_framework.py`：F2（root 漂移、绝对路径拒绝）。
  - `test_modes.py`：F1/F3（文档缺失、扩展点警告）、T1（slice 必填）。
  - `test_tasks.py`：T2（缺 id、成环、自依赖）。
  - 新增 `test_indie_views.py`：R1（`status` 文本 + `--json`）、R2（`--history`）、R3（`doctor` 的 FAIL/OK）。
  - 新增审计测试：V1 在 git 仓库里改受保护文件 → 退出 `1`。
- 全量 `pytest` 必须保持全绿。

## 7. 这次不做，以及为什么

| 事项 | 为什么不做 |
| --- | --- |
| 项目级 roadmap / `bulings plan` | 需要先在 `design.json` 里加功能清单并改定稿流程，会动 schema 和 `--finish` 的语义；先有 `status` 总览，roadmap 再单独做 |
| 切片级验证命令（跑编译/测试） | 和 README「不调用 Unity 批处理编译」的现约定冲突，要单独设计用户显式配置的入口 |
| 工程级缺失清单 `.bulings/gaps.json` | 刚加的缺失分析已经落在 `tasks.json` + 文档里；跨 feature 汇总等 `status` 稳定后再做 |
| 对话版策划案迭代（`/BulingDesign`） | 属于 Skill/命令层，和本次 Python 校验改动耦合小，单独做 |
| 定稿后 `--reopen` 改策划案 | 会和 D2 的「定稿必须四维确认」相互影响，要先想清楚撤销语义 |
| 把缺失分析规则从提示词挪回 Skill | 之前正是 Skill 没加载时提示词兜底；挪走会回归，保留一行摘要 |
