# 12 界面验收

先读 [00-索引与共同约定](00-索引与共同约定.md)。前置是 [04-需求确认](04-需求确认.md)、[08-候选与独立评审](08-候选与独立评审.md) 和 [10-验证与封存](10-验证与封存.md)。

## 目标

在同一套交付档案上增加界面配置。开工前核对预制体、协议、配置和需求描述，并用用户原文确认可以开工的切片。结束前生成一张验收页；用户对当前结果的原文被记录后，封存才成功。

## 本任务产出

- `references/ui.md`
- `init` 接受 `--profile ui`
- 开工清单、场景验收记录、验收页和最终确认
- `tests/test_delivery_ui.py`

不实现 Unity 编辑器程序，不启动 Unity。截图以调用者提供的、已经存在的图片文件为证据。

## 配置

`bulings delivery init` 增加可选 `--profile`，取值 `delivery` 或 `ui`，默认 `delivery`。`ui` 时 `feature.json` 的 `profile` 为 `ui`。任务 01 的重复初始化规则不变：已存在档案的 `profile` 与参数不一致时失败，不改写。

`references/ui.md` 规定：

- 先从需求场景找可见操作和结果，再记录承载它的现有 Prefab。
- 找不到 Prefab 时记 `not-found`，不创建占位预制体。
- 多个候选记 `ambiguous`，并列出至少两个存在的 `.prefab` 路径。
- 截图只证明位置。运行结果写在场景验收记录里。
- `reuse` 表示产品文件不需要修改。改接线、显示、布局或文案都用 `change`。

## 开工清单

```powershell
bulings delivery prepare-ui-baseline --project <工程> --feature-id <id>
```

仅 `profile` 为 `ui` 时可用。写入 `02-investigation/ui-baseline.json`，已存在则返回路径且不覆盖。

调用者提交的结构：

```json
{
  "schema": 1,
  "items": [
    {
      "scenario": "领取奖励",
      "prefabs": [
        {"status": "verified", "path": "Assets/UI/Reward.prefab", "purpose": "领取按钮"}
      ],
      "protocols": [
        {"status": "not_applicable", "purpose": "本场景不新增协议"}
      ],
      "configurations": [
        {"status": "inherited", "path": "Assets/Config/Reward.json", "purpose": "沿用奖励表"}
      ],
      "requirement": {"status": "verified", "purpose": "点击后剩余次数减一"}
    }
  ],
  "excludedSources": []
}
```

`scenario` 必须是需求场景名，且每个需求场景恰好一项。`status` 为 `verified`、`inherited`、`missing`、`ambiguous`、`not_applicable`。

- `verified` 和 `inherited` 的 `path` 必须存在。`inherited` 只能用于协议和配置。
- `not_applicable` 只能用于协议和配置，且不能有 `path`。
- 预制体和需求不允许 `not_applicable`。
- `ambiguous` 的预制体要有 `candidates` 数组，至少两个存在的路径。
- `missing` 要有非空 `purpose`，说明缺什么。

```powershell
bulings delivery check-ui-baseline --project <工程> --feature-id <id>
```

返回每个场景的 `ready` 布尔值。四类材料都没有 `missing` 和 `ambiguous` 时，该场景 `ready` 为 true。

## 开工确认

```powershell
bulings delivery approve-ui-baseline --project <工程> --feature-id <id> --scenario 领取奖励 --decision approve --locator <位置> --user-confirmation <原文>
```

`--scenario` 可重复。每个场景必须是 `ready`。原文和定位非空。批准写入 `approvals.uiBaseline.scenarios[<场景名>]`，并保存清单文件摘要。

清单文件变化后，受影响场景的批准在 `status` 中变为 `stale`。`start-slice` 在 `profile` 为 `ui` 时增加一条检查：该切片任务包里的 `scenarios` 数组每一项都有未过期的 `approve`。任务包因此增加必填 `scenarios`，取值来自需求场景名。普通 `delivery` 配置不要求这个字段。

未确认的场景不影响其他场景的 `start-slice`。

## 场景验收记录

实施期间写入 `06-validation/acceptance.json`：

```json
{
  "schema": 1,
  "smoke": {
    "status": "unverified",
    "entry": "从主界面打开奖励",
    "note": "编辑器未连接，尚未打开真实入口"
  },
  "scenarios": [
    {
      "scenario": "领取奖励",
      "level": "static",
      "status": "unverified",
      "actual": "",
      "evidence": []
    }
  ]
}
```

`level` 为 `static`、`isolated`、`runtime`。`status` 为 `passed`、`failed`、`unverified`。`runtime` 且 `passed` 时，`evidence` 至少有一个存在的文件。`smoke.status` 为 `passed` 时，`note` 改为非空的实际观察，并增加存在的 `evidence` 路径。

提供 `record-acceptance`，参数用一个 `--input` JSON 文件整体替换这份记录。文件内容不合法时不覆盖旧文件。

## 验收页

```powershell
bulings delivery publish-ui --project <工程> --feature-id <id>
```

读取已接受候选、开工清单和 `acceptance.json`，生成 `06-validation/ui-delivery.html`。页面用中文显示每个场景的变化目的、入口、验证层级、状态、实际结果和证据相对路径。`unverified` 的场景显示「未验证」。没有已接受候选时也可以生成，此时页面顶部写「尚未形成可封存结果」。

命令返回 `deliveryReady`。只有全部保留场景的 `level` 为 `runtime`、`status` 为 `passed`，且 `smoke.status` 为 `passed` 时为 true。

## 封存差异

`profile` 为 `ui` 时，`freeze-delivery` 在任务 10 的条件之外还要求：

- `publish-ui` 已经生成 HTML，且 `deliveryReady` 为 true。
- 存在 `approvals.final`，`decision` 为 `approve`，`userConfirmation` 非空，并且它记录的 `htmlDigest` 等于当前 HTML 字节摘要。

```powershell
bulings delivery approve-final --project <工程> --feature-id <id> --decision approve --locator <位置> --user-confirmation <原文>
```

摘要不匹配、`deliveryReady` 为 false、或原文为空时失败，不写入批准。普通 `profile: delivery` 调用 `approve-final` 时失败，`code` 为 `PROFILE_MISMATCH`，封存仍按任务 10，不需要这条命令。

`completion.claim` 在 `profile` 为 `ui` 且生命周期还不是 `frozen` 时，即使验证结论已经 `passed`，也保持 `in_progress`，`reason` 写明等待用户验收。

## 测试

- 缺预制体的场景 `ready` 为 false，不能被批准。
- 批准一个就绪场景后，另一个缺失场景不使已批准场景失效。
- 修改清单文件后，已批准场景变为 `stale`，对应 `start-slice` 失败。
- 验收记录全是 `static` 时页面生成成功，`deliveryReady` 为 false，冻结失败。
- 记录改为 `runtime` 且证据文件存在、用户原文被批准后，冻结成功。
- 改动 HTML 后旧的最终批准不能再用于冻结。
- `profile: delivery` 的封存不要求 HTML。
