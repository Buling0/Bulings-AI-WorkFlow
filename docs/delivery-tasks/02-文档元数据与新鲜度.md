# 02 文档元数据与新鲜度

先读 [00-索引与共同约定](00-索引与共同约定.md)。前置是已完成的 [01-交付档案初始化](01-交付档案初始化.md)。

## 目标

六份阶段总览和术语表带上统一元数据。调用者保存正文后，用显式命令声明这一批编辑是否改变语义。语义变化使直接下游过期；过期文档不能通过新鲜度检查。

## 本任务产出

- 初始化时写入本任务规定的 YAML 前置。任务 01 的「待填写」标题保留在前置之后。
- `confirm-change`、`refresh-queue`、`assert-fresh`。
- 术语表的空章节检查。
- `tests/test_delivery_documents.py`。

切片、批准和 Skill 不在本任务。

## 前置元数据

每份受管 Markdown 以 YAML 前置开始：

```yaml
---
id: building-interaction.requirements.overview
contentStatus: draft
semanticVersion: 0.1.0
fingerprint: sha256:<正文 UTF-8 的 SHA-256>
dependencies: []
dependencyVersions: {}
relatedDocuments: []
staleFromStatus: draft
---
```

标识使用索引中的总览标识。术语表标识是 `<feature-id>.requirements.terminology`。

`contentStatus` 取值：`draft`、`ready`、`stale`、`blocked`。`fingerprint` 只覆盖前置之后的正文，包含正文开头的换行。`dependencies` 和 `relatedDocuments` 是文档标识列表。`dependencyVersions` 是标识到语义版本的映射。

初始化时的依赖只有一条：需求总览依赖本交付项的术语表，`dependencyVersions` 记下术语表的 `0.1.0`。其他文档的依赖列表为空。

## 确认变更

```powershell
bulings delivery confirm-change --project <工程> --feature-id <id> --document-id <文档标识> --semantic-change true
```

`--document-id` 可重复，表示同一批。命令读取磁盘上已经保存的正文。

- 正文和依赖都没变：返回 `unchanged`，不改版本，不改 `updatedAt`。
- `--semantic-change false`：更新指纹。若该文档当前是 `stale`，把 `contentStatus` 设回它的 `staleFromStatus`，并把 `dependencyVersions` 更新为依赖文档的当前语义版本。自身语义版本不变，它的下游不变。
- `--semantic-change true`：指纹更新，语义版本的补丁号加 1（`0.1.0` 变为 `0.1.1`）。只把直接依赖它的文档标为 `stale`。被标过期的文档若原来不是 `stale`，把它当时的 `contentStatus` 写入自己的 `staleFromStatus`。
- 一批里既有语义变化又有非语义变化时，只提升标成语义变化的那些文档的版本。本命令对整批使用同一个布尔值；调用者把两种变化分成两次调用。

确认必须原子：先写临时文件，再替换涉及的 Markdown 和 `feature.json` 的 `updatedAt`。中途失败不留下新前置。

拒绝这些输入：未知文档标识、前置损坏、依赖指向不存在的文档、自己依赖自己、依赖指向同一阶段或更后阶段（术语表被需求总览依赖是唯一例外）、`contentStatus` 取值非法。

`lifecycle` 为 `frozen` 或 `pending_cleanup` 时拒绝确认。本任务还没有把生命周期改成这两种值的命令；测试可以直接改 `feature.json` 来覆盖拒绝。

## 新鲜度

```powershell
bulings delivery refresh-queue --project <工程> --feature-id <id>
bulings delivery assert-fresh --project <工程> --feature-id <id> --document-id <文档标识>
```

队列包含两类文档：`contentStatus` 为 `stale` 的，以及 `dependencyVersions` 与依赖文档当前 `semanticVersion` 不一致的。按阶段顺序再按标识排序。冻结交付项返回空队列，即使文件上仍写着 `stale`。

`assert-fresh` 可重复 `--document-id`。全部新鲜时退出码 0，`status` 为 `fresh`。任一过期时退出码 1，`code` 为 `STALE_DOCUMENT`，`blockers` 列出文档标识。

## 术语表正文

前置之后保持两个二级标题：「已确认术语」「候选术语」。没有术语时两个章节除标题外为空，校验通过。

出现术语时，每个术语是三级标题，其下有列表项「状态」「一句话定义」。状态只能是「已确认」或「候选」，并且必须位于对应的二级章节。同一交付项里三级标题和「别名」中的名称不能重复。别名行可选。

本任务只校验这个结构，不提供跨文件重命名。定义变化由调用者编辑术语表后执行 `confirm-change --semantic-change true`。

## 链接

阶段文档里的普通相对 Markdown 链接必须指向存在的相对文件。指向术语标题的链接在本任务只检查文件存在，不检查锚点。代码围栏、行内代码和 `http` 链接不参与检查。`assert-fresh` 不检查链接；另提供库函数 `validate_delivery(project, feature_id)`，供 `status --feature-id` 在任务 01 的摘要之外附加 `documentErrors`。没有错误时该数组为空。任务 01 的无标识列表不因此扫描正文。

## 测试

- 新档案的需求总览依赖术语表，指纹与正文一致。
- 改术语表正文并做语义确认后，需求总览进入队列，`assert-fresh` 失败。
- 需求总览做非语义确认后离开队列，术语表版本仍是加过一次的版本，需求总览自身版本不变。
- 需求总览再做语义确认时，只把它的直接下游标过期。初始化状态下它没有下游，计划总览保持原状态。
- 手工把计划总览的依赖写成需求总览后，语义确认需求总览会使计划总览过期；计划总览做非语义确认后，实施总览即使依赖计划总览也不过期。
- 自依赖、后向依赖、重复术语标题、冻结后的确认都被拒绝。
- 无变化的重复确认返回 `unchanged`。
