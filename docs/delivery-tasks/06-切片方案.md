# 06 切片方案

先读 [00-索引与共同约定](00-索引与共同约定.md)。前置是 [05-调查与设计评审](05-调查与设计评审.md)。`design-ready` 未通过时，本任务的检查和批准都失败。

## 目标

计划按可以分别接受或退回的结果声明切片。机器检查关系合法后，协调者批准一个带摘要的方案版本。批准后的方案才能被任务 07 启动。

## 本任务产出

- `references/plan.md`
- `04-plan/slice-plan.json` 的草稿、检查和批准
- `tests/test_delivery_slice_plan.py`

不创建写入租约，不修改 Unity 的 `Assets`。

## 计划总览

`references/plan.md` 要求 `04-plan/README.md` 在前置之后包含：

```markdown
# 计划

## 拆分

- 结果：<可单独验收的结果>
  切片：<slice-id>
  场景：<需求场景名>
  理由：<为什么能分开验收，或为什么和另一结果放在一起>

## 共同依赖

没有则写「无」。有则写明决定和依据来自设计总览的哪一个变化名。
```

规则要求：编码、配置和测试不因为文件不同就拆成多个切片；两个结果必须一起改同一责任时写成一个切片，并在理由里说明。程序检查每个切片至少出现一次，每个需求场景名至少被一个切片的「场景」引用。

提供命令把计划总览的依赖设为设计总览：

```powershell
bulings delivery prepare-plan --project <工程> --feature-id <id>
```

`design-ready` 失败时该命令失败。

## 方案文件

```powershell
bulings delivery prepare-slice-plan --project <工程> --feature-id <id>
```

在 `04-plan/slice-plan.json` 不存在时写入草稿。已存在时返回 `unchanged`，不覆盖编辑。

```json
{
  "schema": 1,
  "featureId": "building-interaction",
  "version": 1,
  "slices": [
    {
      "id": "show-reward",
      "title": "展示奖励",
      "dependsOn": [],
      "replaces": []
    }
  ]
}
```

切片 `id` 使用与 `feature-id` 相同的字符规则。`dependsOn` 是直接前置切片，`replaces` 是被本切片替代的切片。列表都只放直接关系，不写传递闭包。

## 检查

```powershell
bulings delivery check-slice-plan --project <工程> --feature-id <id>
```

检查：

- `featureId` 与档案一致，`version` 是正整数。
- 至少有一个切片，标识不重复。
- `dependsOn` 和 `replaces` 指向同文件中的其他切片。
- 前置图和替代图都无环。
- 一个切片不能直接或间接依赖自己替代的切片，也不能依赖替代链上的切片。
- 计划总览的「切片」列与方案标识集合一致。
- 计划总览新鲜，且 `design-ready` 通过。

成功时返回 `valid`、规范化后的切片数组，以及 `digest`。摘要是规范化 JSON 的 UTF-8 SHA-256。规范化规则：对象键按字母排序，切片按 `id` 排序，数组保持依赖声明的去重后顺序，`dependsOn` 与 `replaces` 按标识排序。不要把摘要算进被摘要的 JSON。

失败时退出码 1，`blockers` 包含 `SLICE_CYCLE`、`UNKNOWN_SLICE`、`PLAN_MISMATCH`、`DESIGN_NOT_READY` 之一。

## 批准

```powershell
bulings delivery approve-slice-plan --project <工程> --feature-id <id> --digest sha256:<检查结果>
```

命令重新做一遍检查。摘要不一致则失败，`code` 为 `DIGEST_MISMATCH`，不写入批准。

成功时写入 `04-plan/slice-plan.approved.json`，内容是规范化方案加 `digest`、`approvedAt`。同一 `version` 再次批准且摘要相同，返回 `unchanged`。同一版本摘要不同则拒绝，要求调用者把草稿 `version` 加 1。新版本批准后，旧的 `slice-plan.approved.json` 移到 `04-plan/history/slice-plan-v<旧版本>.json`，新文件成为当前批准。

`status --feature-id` 增加：

```json
{
  "slicePlan": {
    "version": 1,
    "digest": "sha256:...",
    "sliceIds": ["show-reward"]
  }
}
```

没有批准文件时 `slicePlan` 为 `null`。

同时返回每个切片的 `eligibility`：`ready` 或 `waiting`。没有未完成的前置、且没有未完成的被替代切片时为 `ready`。本任务还没有切片执行状态，全部切片都是 `ready`，除非它 `dependsOn` 非空：有前置的切片为 `waiting`。替代关系同样使替代者在被替代者未完成时 `waiting`。任务 08 会把已接受切片算作完成；本任务把所有切片都视为未完成，因此只有没有前置且不替代别人的切片是 `ready`。

## 测试

- 两个互不依赖的切片可以通过，有前置的那个是 `waiting`。
- A 依赖 B、B 依赖 A 时失败。
- 计划正文漏了一个切片标识时 `PLAN_MISMATCH`。
- 批准后改草稿但不升版本，再次批准失败，历史文件不产生。
- 升版本并重新批准后，旧版本出现在 `history/`，`status.slicePlan.version` 是新版本。
- `design-ready` 失败时检查失败，且不生成批准文件。
