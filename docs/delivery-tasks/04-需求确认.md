# 04 需求确认

先读 [00-索引与共同约定](00-索引与共同约定.md)。前置是 [02-文档元数据与新鲜度](02-文档元数据与新鲜度.md) 和 [03-协调者入口](03-协调者入口.md)。

## 目标

需求总览按可单独判断的业务场景书写。协调者把冷读交给一份不含前序结论的提示。用户用真实回复确认后，批准绑定当时的需求指纹；需求再发语义变化时批准失效。

## 本任务产出

- `pack/skills/delivery/references/requirements.md`
- `bulings delivery rules --action requirements` 返回该文件。
- `bulings delivery approve-requirements`
- `bulings delivery cold-read-prompt`
- 需求总览的结构校验。
- `tests/test_delivery_requirements.py`

调查、设计和切片不在本任务。

## 需求总览正文

前置之后，正文按这个结构维护：

```markdown
# 需求

## 当前决定

这一节写本次需要人决定的事项。没有待决定项时写「无」。

## 场景

### <场景名>

- 主体：
- 初始条件：
- 操作：
- 可观察结果：
- 来源：<策划或资料的相对路径>#<可复核定位>

## 非目标
```

至少有一个场景。四个列表项都要有非空内容。「来源」在文件存在时通过；用户尚未提供文件时允许写「待提供：<缺什么>」，此时 `approve-requirements` 拒绝批准。

场景名在本交付项内唯一。不要按控件、Prefab 或文件拆场景。取消和失败可以写在同一场景的「可观察结果」里。

`references/requirements.md` 用中文把以上结构写成协调者规则，并规定：实现细节未知时写入调查阶段，不要求用户先拆任务；交给用户的只是会改变目标、外部行为、验收或范围的分叉。

## 冷读提示

```powershell
bulings delivery cold-read-prompt --project <工程> --feature-id <id> --question <入口问题>
```

命令不启动 Agent。成功时返回：

```json
{
  "featureId": "building-interaction",
  "role": "cold-read",
  "prompt": "<完整提示文本>",
  "materials": [
    ".bulings/deliveries/building-interaction/01-requirements/README.md",
    ".bulings/deliveries/building-interaction/01-requirements/terminology.md"
  ]
}
```

提示文本必须包含：

- 角色是冷读，只根据 `materials` 回答入口问题。
- 入口问题的原文。
- 要求把每个结论标成「直接说明」「只能推断」「没有说明」「存在歧义」之一。
- 禁止读取实施目录、禁止根据常识补全、禁止修改文件。

需求总览缺少「场景」或仍含「待填写」时，命令失败，`code` 为 `MATERIAL_MISSING`。

Skill 的协调者规则补一句：冷读使用新的 Agent 对话，不把当前对话历史贴进提示；提示只用本命令的 `prompt`。本任务不把 Cursor SDK 调用接进 `cold-read-prompt`。

## 批准

```powershell
bulings delivery approve-requirements --project <工程> --feature-id <id> --decision approve --locator <回复位置> --user-confirmation <用户原文>
```

`--decision` 为 `approve` 或 `reject`。`locator` 和 `user-confirmation` 去空白后非空。

批准前检查：

- 需求总览和术语表通过 `assert-fresh`。
- 需求结构校验通过，且没有「待提供」。
- 生命周期是 `draft` 或 `active`。`draft` 在批准成功时改为 `active`。

成功后把批准写入 `feature.json` 新字段 `approvals.requirements`：

```json
{
  "decision": "approve",
  "documentId": "building-interaction.requirements.overview",
  "semanticVersion": "0.1.0",
  "fingerprint": "sha256:...",
  "locator": "对话 14:22",
  "userConfirmation": "按这个范围做",
  "confirmedAt": "2026-10-27T00:00:00+00:00"
}
```

拒绝时同样写入，`decision` 为 `reject`，生命周期保持原值。

之后若需求总览或术语表的指纹与批准时不同，`status --feature-id` 的新字段 `approvalState.requirements` 为 `stale`。指纹一致时为 `approved` 或 `rejected`。从未批准时为 `missing`。程序不删除历史字段；最新一次决定覆盖 `approvals.requirements`。覆盖前的决定不必另存历史。

`status` 在本任务增加 `approvalState`，不要去掉任务 01 已有字段。

## 测试

- 合格需求可以批准，生命周期变为 `active`，原文被保存。
- 空原文、缺少场景、来源仍是「待提供」、文档过期时拒绝，且 `feature.json` 不变。
- 批准后对需求总览做语义确认，`approvalState.requirements` 变为 `stale`。
- 冷读提示包含问题原文和四个标记词，且不包含 `05-implementation` 的正文。
- `rules --action requirements` 返回的正文含「场景」和「待提供」。
