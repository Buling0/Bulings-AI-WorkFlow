# 05 调查与设计评审

先读 [00-索引与共同约定](00-索引与共同约定.md)。前置是 [04-需求确认](04-需求确认.md)。

## 目标

调查文档只记录事实和未知。设计文档记录方案。出现规定的外部行为变化时，实施前必须有一份独立设计评审提示；评审未通过时，后续任务不得把该设计当作已可实施。

## 本任务产出

- `references/investigation.md`、`references/design.md`
- `rules --action investigation` 与 `rules --action design`
- `record-design-review` 命令，把评审结论写入 `feature.json`
- `design-review-prompt` 命令
- `tests/test_delivery_design.py`

本任务不创建切片，也不启动 Agent。

## 调查总览

`references/investigation.md` 规定 `02-investigation/README.md` 的正文：

```markdown
# 调查

## 事实

### <事实标题>

- 证据：<工程相对路径>#<定位>
- 说明：

## 未知

### <问题>

- 影响：
- 阻塞：是或否
```

证据路径必须存在。「阻塞」为「是」的未知仍然存在时，`record-design-review` 和本任务新增的 `design-ready` 查询都失败，`code` 为 `INVESTIGATION_BLOCKED`。没有未知时保留「未知」标题，下面写「无」。

调查可以引用需求场景名，但不改写需求。规则里写明：多个互不依赖的事实可以由协调者分多次只读查看；写入调查总览仍由当前对话串行完成。本任务不实现并行子进程。

## 设计总览

`references/design.md` 规定：

```markdown
# 设计

## 方案

用一段话说明选择和取舍。

## 变化

### <变化名>

- 类型：内部整理 或 外部行为
- 场景：<需求里的场景名>
- 行为：
- 不变量：
```

「类型」只有这两个值。`外部行为` 包括：新的独立职责模块、公共接口变化、跨模块状态归属变化、权限或数据安全、回滚约定、用户能观察到的新错误或新执行顺序。规则正文列出这几类，供协调者分类，程序只检查类型字段的字面值。

每个「场景」必须等于需求总览里的一个场景名。设计总览的 `dependencies` 在第一次 `confirm-change` 前由本任务的 `prepare-design` 写成需求总览和调查总览，并记录二者当前语义版本。`prepare-design` 在依赖已正确时返回 `unchanged`。

```powershell
bulings delivery prepare-design --project <工程> --feature-id <id>
```

需求批准不是 `approved`，或调查仍有阻塞未知时，`prepare-design` 失败。

## 设计评审

存在任一「外部行为」变化时需要评审。全部变化都是「内部整理」时，`design-review-prompt` 失败，`code` 为 `REVIEW_NOT_REQUIRED`，并且 `design-ready` 在设计文档新鲜时返回 `ready`。

```powershell
bulings delivery design-review-prompt --project <工程> --feature-id <id>
```

返回的 `prompt` 包含：角色是设计评审；只读材料和允许路径是需求总览、调查总览、设计总览；要求给出 `pass`、`fail` 或 `unverified`；要求指出更简单的替代是否存在；禁止修改工程。提示不包含实施目录路径。材料过期或设计仍是「待填写」时失败。

```powershell
bulings delivery record-design-review --project <工程> --feature-id <id> --decision pass --summary <一段结论>
```

`--decision` 为 `pass`、`fail`、`unverified`。`summary` 非空。结论写入 `approvals.architecture`：

```json
{
  "decision": "pass",
  "documentId": "building-interaction.design.overview",
  "semanticVersion": "0.1.1",
  "fingerprint": "sha256:...",
  "summary": "职责放在现有交互模块内。",
  "confirmedAt": "2026-10-27T00:00:00+00:00"
}
```

`design-ready` 成功条件：

- 需求批准为 `approved` 且不是 `stale`。
- 调查没有阻塞未知，调查和设计文档新鲜。
- 若存在外部行为变化，`approvals.architecture.decision` 为 `pass`，且指纹等于当前设计总览。

否则退出码 1，`blockers` 写明缺哪一条。设计总览语义变化后，架构批准在 `status` 里显示为 `stale`。需求批准变成 `stale` 时，架构批准也显示为 `stale`，即使设计指纹没变。

## 测试

- 只有内部整理时，`design-ready` 在文档新鲜且需求已批准时成功，且不要求架构批准。
- 有外部行为变化但没有评审记录时，`design-ready` 失败。
- `pass` 之后修改设计并做语义确认，架构状态变为 `stale`。
- 调查里留着阻塞未知时，不能记录评审。
- 设计引用了需求中不存在的场景名时，`prepare-design` 之后的结构校验失败。
- 评审提示同时含需求、调查、设计三份相对路径，不含 `05-implementation`。
