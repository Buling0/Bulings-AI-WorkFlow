# 交付流实现任务：索引与共同约定

本目录把「在 Bulings 中实现一条类似 DLoop 的长任务交付流」拆成按顺序实现的子任务。一次只实现一个编号。实现前先读本文，再读该编号文档，并只改该文档点名的代码。

对照来源是 [DLoop 工作流说明](../DLoop-工作流说明.md)。那份文档描述的是上游仓库 v4.0.3 的完整行为。本系列取它的交付结构，落在当前 Bulings 仓库里，不移植 DLoop 源码。

## 现有工作模式保持不动

当前仓库已经有一条短流程：

- Skill：`pack/skills/work-feature/`
- 命令：`bulings init`、`bulings run`、`bulings resume`
- 状态：`.bulings/runs/<slug>/tasks.json`
- 行为：分析策划案和预制体，一次把一个任务交给本机 Cursor Agent

交付流与它并存。`mode: indie` 时两条流程都在启动 Agent 前停止。现有测试 `tests/test_tasks.py`、`tests/test_config.py`、`tests/test_install.py` 必须继续通过。安装器已经会复制 `pack/skills/` 下的每个子目录，新增 Skill 目录会被 `bulings init` 一并装进 Unity 工程的 `.cursor/skills/`。

## 交付流要做成什么样

一条交付流处理跨多轮、需要独立评审和最终验证的功能。人确认会改变目标或验收的决定；已确认范围内由协调者持续推进。局部小改继续走 `work-feature`，不建交付档案。

完成后，一次交付具备这些能力：

1. 显式命令创建或恢复一个交付项，档案分需求、调查、设计、计划、实施、验证六段。
2. 文档语义变化后，下游材料被标成过期，过期材料不能当作实施输入。
3. 需求按业务场景书写，冷读通过后由用户原文确认。
4. 调查只记录可证明的事实；会改变外部行为的设计在实施前单独评审。
5. 计划按「可以分别接受或退回的结果」拆切片，并经过机器检查后批准。
6. 全流程同时只有一个切片持有写入租约，范围外的新改动不能形成候选。
7. 实施者提交候选后，另一个 Agent 上下文只读评审。自评被拒绝。
8. 普通测试失败留在实施里修；契约边界失效才熔断。
9. 切片全部收敛后做整体验证。普通交付自动封存。界面交付要等用户验收原文。
10. 阶段保存点放在交付项自己的本地 Git 库，不改 Unity 工程的分支、暂存区，也不自动提交。

## 本系列不做的上游能力

以下能力留在 DLoop 说明里，本系列不实现，后续任务也不要顺手补上：

- Codex、Claude Code、OpenCode、DeepSeek，以及多宿主 Skill 复制。
- SVN 提交组、子模块独立工作流。
- MCP 服务、`uv`、Unity 编辑器截图包、批处理启动 Unity。
- 安装锁、跨版本归档旧作业、分享快照、摩擦日志。
- 自动 `git commit`、`git push`、修改 `.meta` 的 guid、把交付档案写进长期知识库。

Unity 工程需要是 Git 工作区，交付流用它做范围检查。没有 `.git` 时，启动切片的命令失败并说明原因。

## 共同约定

### 位置

正式档案只在 Unity 工程内：

```text
.bulings/deliveries/<feature-id>/
  feature.json
  01-requirements/README.md
  01-requirements/terminology.md
  02-investigation/README.md
  03-design/README.md
  04-plan/README.md
  05-implementation/
  06-validation/README.md
```

`<feature-id>` 只允许小写英文、数字和连字符，长度 1 到 64，且不能以连字符开头或结尾。中文标题放在 `feature.json` 的 `title`。

机器状态、租约、候选和快照由各自任务规定额外文件名。正式 Markdown 和正式 JSON 使用 UTF-8、无 BOM、LF。命令成功时把 JSON 打到标准输出，可诊断失败把 JSON 打到标准错误。

交付流命令的退出码：

| 码 | 含义 |
|---|---|
| 0 | 成功 |
| 1 | 可诊断的业务或环境失败 |
| 2 | 参数不合法 |

这与 `bulings run` 的退出码不同。实现交付流时保持 `run` / `resume` 的原退出码。

### 代码

新逻辑放在 `bulings/delivery/`。命令挂在 `bulings delivery ...`，由 `bulings/cli.py` 分发。库函数接收路径和结构化参数，打印和退出码留在命令层，方便测试直接调用库。

错误 JSON 至少包含 `code` 和 `message`。需要时加 `blockers` 数组，每项含 `code`、`message`，以及可选的 `path`。

### 时间与指纹

时间使用带时区的 ISO 8601，测试可以传入 `now`。正文指纹是 UTF-8 字节的 SHA-256，写成 `sha256:<十六进制>`。语义是否变化由调用者显式传入，程序不猜测自然语言。

### 用户原文

凡是登记用户确认的命令，都要求非空的 `user_confirmation` 原文和 `locator`。程序不连接对话记录，不把空字符串、`继续` 的默认值或调用者省略的字段当成确认。

### 测试

使用 pytest，在临时目录构造 Unity 工程（含 `Assets`、`ProjectSettings` 和 `git init`）。不访问网络，不启动 Unity，不调用 Cursor Agent。涉及 Agent 的任务只断言交接提示的内容，用假的执行器验证命令会把这份提示交给新的 Agent 标识。

每个任务结束时，该任务列出的测试和原有三份测试文件都要通过。

### 实现者怎么使用一篇任务文档

1. 读本文的共同约定。
2. 只实现当前编号。前置任务未完成时停下来说明缺什么，不要在同一轮把后续编号一起做掉。
3. 按该文档的数据合同实现。合同里没有的字段不要自行增加。
4. 完成后跑该文档列出的测试。不要修改本目录的任务文档来勾选进度。

## 阶段与文档标识

阶段目录和文档标识在 01、02 固定，后续任务直接使用：

| 阶段 | 目录 | 总览标识 |
|---|---|---|
| 需求 | `01-requirements` | `<feature-id>.requirements.overview` |
| 术语 | `01-requirements/terminology.md` | `<feature-id>.requirements.terminology` |
| 调查 | `02-investigation` | `<feature-id>.investigation.overview` |
| 设计 | `03-design` | `<feature-id>.design.overview` |
| 计划 | `04-plan` | `<feature-id>.plan.overview` |
| 实施 | `05-implementation` | `<feature-id>.implementation.overview` |
| 验证 | `06-validation` | `<feature-id>.validation.overview` |

依赖只能指向更早的阶段。唯一的同阶段依赖是术语表指向需求总览之前的反向关系：需求总览依赖术语表。这个方向在 02 实现。
