# 10 验证与封存

先读 [00-索引与共同约定](00-索引与共同约定.md)。前置是 [02-文档元数据与新鲜度](02-文档元数据与新鲜度.md) 和 [08-候选与独立评审](08-候选与独立评审.md)。任务 09 的 `released` 切片在本任务视为已经离开当前方案；若当前批准方案仍包含它，则方案未收敛。

## 目标

当前方案的每个切片都已接受后，协调者写入整体验证。材料齐备时封存交付项。状态里的完成口径阻止在候选未完成时声称整体完成。普通交付不等待用户再说一次「验收通过」。

## 本任务产出

- `references/validation.md`
- `begin-validation`、`record-validation`、`freeze-delivery`
- `status` 中的 `completion` 字段
- `tests/test_delivery_freeze.py`

界面交付的额外用户验收在任务 12。本任务的 `profile` 仍只有 `delivery`，封存不读取用户原文。

## 进入验证

```powershell
bulings delivery begin-validation --project <工程> --feature-id <id>
```

通过条件：

- 全局 `lease` 为 `null`。
- 当前批准方案里的每个切片在 `slice-state.json` 中都是 `accepted`。
- 每个已接受切片都有一条 `decision` 为 `pass` 的评审，且评审执行标识不同于实施执行标识。
- 需求、调查、设计、计划四份总览新鲜，需求批准不是 `stale`。需要架构批准时，架构批准也不是 `stale`。
- 生命周期是 `active`。

成功后生命周期改为 `validating`，`feature.json` 的 `updatedAt` 更新。已是 `validating` 且条件仍成立时返回 `unchanged`。

## 验证正文

`references/validation.md` 规定 `06-validation/README.md`：

```markdown
# 验证

## 场景结果

### <需求场景名>

- 实际结果：
- 证据：<工程相对路径>#<定位>
- 偏差：无，或一段说明

## 未验证边界

无，或具体列表。

## 残留风险

无，或具体列表。

## 后续接入

无，或「影响 / 缺什么 / 谁补 / 补齐后如何验证」。
```

每个需求场景名都要有一节。「证据」路径必须存在。偏差不是「无」时，不能把结论记为通过。

```powershell
bulings delivery record-validation --project <工程> --feature-id <id> --conclusion passed --unverified none --risks none
```

只在生命周期为 `validating` 时可用。`--conclusion` 为 `passed` 或 `failed`。`--unverified` 和 `--risks` 为 `none` 或 `documented`。

`passed` 还要求：每个场景的偏差都是「无」，两个章节与参数一致——参数是 `none` 时正文对应章节只有「无」，参数是 `documented` 时正文不能只有「无」。`failed` 不改生命周期。

命令把三个值写入 `feature.json` 的 `validation`，并对验证总览执行一次语义确认，使它的指纹更新。调用者应先写好正文。正文仍是「待填写」时失败。

## 集成确认

`record-validation` 在结论为 `passed` 时，同时写入 `06-validation/integration.json`：

```json
{
  "schema": 1,
  "result": "passed",
  "candidateIds": ["c-show-reward-1"],
  "candidateDigest": "sha256:<按候选标识排序后的候选文件字节拼接摘要>",
  "workspaceDigest": "sha256:<全部已接受候选里记录的文件摘要，按路径排序后拼接>"
}
```

任一已接受候选的文件摘要与磁盘当前字节不一致时失败，`code` 为 `WORKSPACE_DRIFT`，不改结论。

## 封存

```powershell
bulings delivery freeze-delivery --project <工程> --feature-id <id>
```

条件：

- 生命周期是 `validating`。
- `validation.conclusion` 是 `passed`，两个边界字段都不是 `pending`。
- 六份总览都不是 `draft`、`stale`、`blocked`。验证总览在 `record-validation` 里变为 `ready`。
- `integration.json` 的摘要仍等于重新计算的结果。
- 没有活动租约。

成功后生命周期为 `frozen`，`frozenAt` 写入当前时间。再次冻结返回 `unchanged`。冻结后 `confirm-change`、`start-slice`、`record-validation` 都拒绝，`code` 为 `FROZEN`。

封存不修改 `Assets`，不创建 Git 提交。

## 完成口径

`status --feature-id` 增加：

```json
{
  "completion": {
    "claim": "frozen",
    "reason": "交付记录已封存"
  }
}
```

`claim` 取值：

| claim | 条件 |
|---|---|
| `frozen` | 生命周期是 `frozen` |
| `in_progress` | 其他所有情况 |
| `blocked` | 存在 `circuit_open` 租约，或存在未接受且方案未替换掉的 `released` 切片 |

`blocked` 优先于 `in_progress`。只有 `frozen` 可以用来向用户说整体完成。`references/validation.md` 写明这句话。

## 测试

- 只接受了方案中的一个切片时，`begin-validation` 失败。
- 全部接受但范围内文件在候选之后被改动，`record-validation` 返回 `WORKSPACE_DRIFT`。
- 场景偏差不是「无」时不能记 `passed`。
- 条件满足时冻结，第二次冻结不改变 `frozenAt`。
- 冻结后语义确认失败。
- 有熔断租约时 `completion.claim` 是 `blocked`。
- 没有候选时 `claim` 是 `in_progress`。
