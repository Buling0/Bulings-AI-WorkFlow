# Bulings AI WorkFlow 使用指南

本指南分三部分：**接入**（怎么装进 Unity 工程、仅本地不提交）、**配置**（workflow.yaml 每一项怎么填）、**使用**（每个命令怎么用、怎么串起来）。参数速查见 [README](../README.md)。

局部小改不需要走这套流程，直接在编辑器里改。独游模式（`mode: indie`）面向小规模游戏：先立框架，再按纵向切片做功能，详见 [独游模式说明](独游模式说明.md)。

---

## 一、整体概览

工作流由两部分组成：

- **Python 命令行 `bulings`**：在本机用 Cursor SDK 拉起 Agent，工作目录是 Unity 工程。
- **Skill 包**（`pack/skills/`）：装进工程的 `.cursor/skills/`，规定 Agent 每个阶段怎么做。Cursor 对话和命令行用的是同一份 Skill。

| 能力 | 命令 | Skill | 产物 |
| --- | --- | --- | --- |
| 前端分离 | `bulings split` | client-split | 客户端需求文档 |
| 工作模式 | `bulings run` / `resume` | work-feature | `tasks.json`、开发说明、功能说明、代码 |
| 策划案迭代 | `bulings design`（`mode: indie`） | indie-design | 策划案、`design.json` |
| 独游模式 | `bulings run` / `resume`（`mode: indie`） | indie-feature | `framework.json`、框架文档、`tasks.json`、开发说明、功能说明、代码 |
| AI 知识库 | `bulings kb` | knowledge-base | `Docs/AI/Knowledge/` |
| Unity MCP | `bulings init` 自动配置 | work-feature/unity-mcp.md | `.cursor/mcp.json` |
| 交付流 | `bulings delivery ...` | delivery | `.bulings/deliveries/` |

通用红线（所有流程都遵守）：不自动创建 git commit、不改 `.meta` 的 guid、不启动 Unity 批处理编译、不改 `protectedPaths` 里的路径。

## 二、接入

### 2.1 环境准备

1. Python 3.10+。
2. Cursor 用户 API key（Cursor Dashboard → Integrations），设为环境变量：
   ```powershell
   $env:CURSOR_API_KEY = "cursor_..."
   ```
3. 在本仓库根目录安装：
   ```powershell
   python -m venv .venv
   .\.venv\Scripts\Activate.ps1
   python -m pip install -e .
   ```
   未激活虚拟环境时，用 `.\.venv\Scripts\python.exe -m bulings` 代替 `bulings`。
4. 目标工程必须有 `Assets` 和 `ProjectSettings`。

### 2.2 执行 init

```powershell
bulings init --project <Unity工程>
```

做三件事：

| 动作 | 位置 | 重复执行时 |
| --- | --- | --- |
| 复制 Skill | `<工程>/.cursor/skills/` | 覆盖更新 |
| 写示例配置 | `<工程>/.bulings/workflow.yaml` | 已存在则保留 |
| 合并 Unity MCP | `<工程>/.cursor/mcp.json` | 已有同名条目不覆盖，文件解析失败则不动 |

升级本仓库后，对每个工程重新执行一次 `init` 即可更新 Skill。

### 2.3 仅本地、不提交

希望这些文件不进版本库，又不想改共享的 `.gitignore`，把下面几行写进工程的 `.git/info/exclude`（只对本机生效）：

```
.cursor/skills/
.cursor/commands/
.cursor/mcp.json
.bulings/
Docs/AI/
```

注意：`Docs/AI/` 包含开发说明、功能说明、客户端需求文档。如果这些文档需要团队共享，不要排除它。SVN 工程请用 SVN 自己的忽略方式。

### 2.4 配置 Unity MCP

1. 在 Unity 里安装并启动你选用的 MCP 插件，记下它怎么连：**HTTP 地址**，或 **stdio 启动命令**。
2. 在 `workflow.yaml` 的 `unity.mcp` 里填写（字段见 3.3），再执行 `bulings init`。
3. `init` 把这一项合并进 `<工程>/.cursor/mcp.json` 的 `mcpServers`，只动 `server` 名字那一项，别的服务不动。
4. 若 `.cursor/mcp.json` 里已经有同名的 `unity` 条目，`init` 不覆盖（可能你手改过），请直接改该文件。
5. 重启 Cursor 或重新加载 MCP，让它读到新条目；使用期间保持 Unity 编辑器打开、服务在运行。

> 默认地址 `http://localhost:8080/mcp` 只是假设值，务必按你的插件核对。

三种写法：

```yaml
unity:
  mcp:
    enabled: true
    server: unity                 # 写进 mcp.json 的名字，多个 MCP 服务时改这里
    url: http://localhost:8080/mcp   # HTTP 方式
    command: ""                   # stdio 方式：填了就优先用 command，url 被忽略
    args: []
```

```yaml
# stdio 例子（具体命令换成你插件的）
unity:
  mcp:
    enabled: true
    server: unity
    url: ""
    command: uvx
    args: [unity-mcp, --port, "8080"]
```

规则（都在 `bulings/install.py` 里，可测）：

| 情况 | `init` 的行为 |
| --- | --- |
| `enabled: false` | 不写 `mcp.json`，提示词里也不提 MCP |
| `command` 有值 | 写 `{command, args}`，忽略 `url` |
| `command` 空、`url` 有值 | 写 `{url}` |
| 两个都空 | 不写 |
| 已有同名 `server` 条目 | 保留原样，不覆盖 |
| `mcp.json` 不是合法 JSON，或 `mcpServers` 不是对象 | 整个文件不动，`init` 静默跳过（`mcp_written: false`） |

**配好之后实际改变什么**：`bulings run` / `design` 拼提示词时会把"MCP 可用"和边界告诉 Agent——

- 工作模式：分析阶段只读；实现阶段可以刷新编译、读控制台、在编辑器里绑定引用，完成标准涉及绑定要用 MCP 回读确认。
- 独游模式：框架阶段用 MCP 确认现状并检查骨架能编译；分析阶段只读；实现阶段刷新编译、读控制台、在编辑器里接线。

MCP 连不上时，Agent 要如实说明并写进 `blockedReason`，不能假装验证过。**注意：`init` 只负责把配置写进 `mcp.json`；能不能连上取决于 Unity 里那个插件是否在运行。**

### 2.5 接入后自检

- `.cursor/skills/` 下有 work-feature、client-split、knowledge-base、delivery、indie-feature、indie-design、buling-ai。
- `.cursor/commands/BulingAI.md` 存在。对话里输入 `/BulingAI`。
- `.cursor/mcp.json` 里有对应条目。
- 配置能被读取：
  ```powershell
  python -c "from bulings.config import load_workflow_config as l; print(l(r'<工程路径>'))"
  ```
- `git status` 里看不到上述新文件（本地排除生效）。

## 三、配置（`.bulings/workflow.yaml`）

约定：**空字符串和空数组表示未配置**。未配置的项，Agent 会从工程推断，写进开发说明的「推断的项目约定」，不当作硬性规范。所有路径可用 `{feature}` 占位，值来自 `--name`，否则取策划案文件名。

### 3.1 基本项

| 键 | 默认 | 说明 |
| --- | --- | --- |
| `mode` | `work` | `work` 或 `indie`。`indie` 时 `run` / `resume` 走独游流程（先立框架，再按切片做功能） |
| `model` | `composer-2.5` | 默认模型，可被 `--model` 覆盖 |

### 3.2 文档

```yaml
docs:
  devSpec:
    enabled: true
    path: Docs/AI/DevSpecs/{feature}.md
  featureDoc:
    enabled: true
    path: Docs/AI/Features/{feature}.md
```

- `devSpec`：开发说明，分析阶段生成，含任务清单与状态。
- `featureDoc`：功能说明，全部任务完成后生成，给维护者看。
- 两者可独立开关；命令行可用 `--no-dev-spec`、`--no-feature-doc`、`--dev-spec`、`--feature-doc` 临时覆盖。
- 即使关闭开发说明，`tasks.json` 仍会写。

### 3.3 Unity MCP

```yaml
unity:
  mcp:
    enabled: true
    server: unity
    url: http://localhost:8080/mcp
    command: ""
    args: []
```

| 键 | 说明 |
| --- | --- |
| `enabled` | `false` 时不写 `mcp.json`，提示里也不会提 MCP |
| `server` | 写入 `mcp.json` 的服务名 |
| `url` | HTTP 方式的地址 |
| `command` / `args` | stdio 方式。填了 `command` 就优先用它，此时 `url` 会被忽略 |

### 3.4 前端分离

```yaml
clientSplit:
  path: Docs/AI/ClientSpecs/{feature}.md
```

客户端需求文档的输出路径，`bulings split --output` 可覆盖。

### 3.5 知识库

```yaml
knowledge:
  enabled: true
  root: Docs/AI/Knowledge
```

- `enabled: false`：`kb` 命令拒绝执行，`run` 也不会传地图。
- 工程已有自己的知识库体系时建议关闭，避免两套并存。
- `root` 下的 `MAP.md` 存在时，`run` 才会把地图交给 Agent。

### 3.6 独游：策划案与框架（`indie`，仅 `mode: indie`）

策划案迭代：

```yaml
indie:
  design:
    path: Docs/AI/GameDesigns/{feature}.md
    rounds: 4          # 建议轮次：玩法 → 剧情 → 风格 → 流程
    options: 3         # 每轮给几个选项，2-5
```

| 键 | 说明 |
| --- | --- |
| `path` | 策划案正文路径，`{feature}` 取策划案名 |
| `rounds` | 建议轮次。超过只提示"可以考虑定稿"，不强制停止 |
| `options` | 每轮要求给几个选项。工作流只校验下限（至少 2 个） |

框架：

```yaml
indie:
  framework:
    enabled: true
    plan: .bulings/indie/framework.json
    doc: Docs/AI/Frameworks/{game}.md
    paradigm: ""
```

| 键 | 说明 |
| --- | --- |
| `enabled` | `false` 时跳过框架阶段，切片仍要写 `new:` 登记扩展点；命令行 `--no-framework` 可临时覆盖 |
| `plan` | 框架清单路径（工程级，Agent 写、工作流校验） |
| `doc` | 框架文档路径，`{game}` 取工程目录名 |
| `paradigm` | 指定范式；留空由 Agent 按 `frameworks.md` 选型 |

工程已有自己一套架构时，把下面的 `project.architecture` / `ui.*` 填清楚，再考虑关掉框架阶段。

### 3.7 项目适配（`project`）

```yaml
project:
  codeRoots: []        # 代码目录
  namespaces: []       # 命名空间
  asmdefs: []          # 程序集
  ui:
    framework: ""      # UI 框架
    binding: ""        # UI 绑定方式
    notes: ""          # UI 补充说明
  architecture: ""     # 架构要点
  style: ""            # 代码风格
  protectedPaths: []   # 这些路径不允许改
```

填得越准，Agent 越不需要猜。重点是 `protectedPaths`：把框架目录、自动生成的代码（绑定类、协议类、配置表类）都列进去。它对 MCP 操作同样有效。

### 3.8 配置示例（真实工程写法）

```yaml
mode: work
model: composer-2.5
knowledge:
  enabled: false          # 工程已有知识库
project:
  codeRoots: [Assets/GameScripts/Runtime]
  asmdefs: [HotUpdate.Code]
  ui:
    framework: SWEngine.UIEx
    binding: "partial class：Bind 下自动生成，Logic 下手写"
  architecture: "热更代码在 Runtime，AOT 在 AOTCode；模块经 GameModule 访问"
  style: "类/方法 PascalCase，私有字段 _camelCase；热更代码避免 LINQ"
  protectedPaths:
    - Assets/GameScripts/Runtime/Framework
    - Assets/GameScripts/AOTCode
    - Assets/GameScripts/Runtime/Proto
    - Assets/GameScripts/Runtime/GameLogic/UI/Bind
```

## 四、使用

下面的命令都在本仓库根目录执行，`--project` 指向 Unity 工程。路径参数可以是绝对路径，也可以是相对工程根的路径。

### 4.1 推荐的总流程

```
init（一次）→ 配置 workflow.yaml → [kb init] → [design] → [split] → run → [resume --confirm-flow] → [kb update]
```

方括号为可选步骤。`mode: indie` 时：没有策划案就先跑 `design`（可以多轮），跳过 `split`，第一次 `run` 会先跑框架阶段。

工作模式默认在分析后停一次：看完流程图再加 `--confirm-flow` 继续；不需要这张图就加 `--no-flow` 或设 `docs.flow.enabled: false`。

### 4.2 前端分离：`bulings split`

适用：策划案里客户端、服务端内容混写，只想开发客户端。

```powershell
bulings split --project <工程> --design <策划案> [--name <功能名>] [--output <路径>] [--model <模型>]
```

Agent 逐条把需求归入：客户端 / 服务端 / 配置 / 待确认。一条需求涉及两端时拆开，客户端只留自己那一半。

输出的客户端需求文档包含：

1. 范围
2. 客户端需求清单（编号 `C1、C2…`，带策划案出处）
3. 服务端依赖（需要什么数据、何时请求，协议未定的会标明）
4. 依赖的配置
5. 涉及的预制体/界面
6. 待确认
7. 已排除（明确属于服务端或配置的条目及去向）

**务必人工复核**「待确认」和「已排除」：核对没有漏项、归属没有错，必要时直接改文档。归属不明的条目 Agent 不会自行归入客户端。

退出码：`0` 成功；`1` 未启动（参数、配置、密钥等）；`2` 已启动但没写出文档。

### 4.3 工作模式：`bulings run`

```powershell
bulings run --project <工程> --design <策划案> --prefab <预制体> [--prefab <预制体> ...] `
  [--name <功能名>] [--dev-spec <路径>] [--feature-doc <路径>] `
  [--no-dev-spec] [--no-feature-doc] [--no-flow] [--model <模型>]
```

做了前端分离时，`--design` 传客户端需求文档。流程：

1. **分析（先做缺失分析）**：读策划案和预制体，先按四类找这次缺什么——**策划**（策划案里没定的规则、数值、要用的配置表）、**后端**（协议号、协议字段和策划要的数据是否对得上）、**美术**（预制体缺节点组件、结构和策划不符、缺 UI 图或特效）、**前端**（显示时机、层级、刷新、空态这类没说清的显示逻辑）。阻断性的（不给就没法按策划实现，或实现了一定和策划不一致）对应任务标 `blocked`，`blockedReason` 以类别开头；非阻断的先用保守做法，记进开发说明的「缺失与待补齐」。然后写 `.bulings/runs/<功能名>/tasks.json` 和**流程图** `.bulings/runs/<功能名>/flow.md`，开启时同时写开发说明。
2. **流程图确认**：分析结束停在 `flow` 阶段，命令退出 `2`，打印流程图路径。看完页面交互和数据流后跑 `bulings resume --project <工程> --run <功能名> --confirm-flow` 才进入实现；`--no-flow` 跳过这张图。
3. **逐项实现**：每轮只交给 Agent 一项任务，完成后标 `done`。实现中才发现新缺失时按同一套判断：阻断就标 `blocked` 停下，非阻断就做完并记进「缺失与待补齐」。
4. **功能说明**：全部 `done` 后生成（开启时），同时把这次的非阻断缺失按四类汇总一遍。

**分析阶段有阻断项时命令退出 `2`**，把阻断项按类别列到终端，不进入写代码。按提示补齐策划案、配置、协议或预制体后 `resume`，`blocked` 任务会改回 `in_progress` 重做。非阻断项不拦流程，最后汇总。

任务状态只有 `pending`、`in_progress`、`done`、`blocked`。同一功能还有未完成的运行时，`run` 不会再开新 Agent，会提示用 `resume`。

工作模式至少要给一个 `--prefab`。

状态文件：`.bulings/runs/<功能名>/state.json`。

**预制体绑定怎么要求**：节点/组件引用优先在预制体内用脚本绑定，顺序是「预制体已有序列化引用 → 工程的绑定脚本/生成器 → Unity MCP 生成并绑定」。不用 `transform.Find`、`GameObject.Find`、按节点名 `GetComponent` 兜底；只有工程本来就这么绑（`project.ui.binding` 写了）或用户要求时才允许，且要写进「已知限制」。绑不了就地生成时，开发说明的「预制体绑定 → 待用户补绑定」会列出「哪个预制体、哪个节点、要绑什么、为什么」，Agent 也会在回复里直接告诉你补哪几个预制体。

**流程图门禁怎么判**：流程图必须包含「页面与入口」「页面交互流程」「数据流向」和至少一张 mermaid 图，最后一行是 `<!-- flow-status: draft -->`；`--confirm-flow` 会检查这些，空壳会被拒绝并列出问题。确认后最后一行变成 `<!-- flow-status: confirmed by user at ... -->`。关闭方式：`--no-flow`（当次）、`docs.flow.enabled: false`（整个工程）。

**缺失分析怎么判**：四个类别各查什么、阻断和非阻断怎么分，见 `.cursor/skills/work-feature/SKILL.md` 的「缺失分析」一节。要点：

| 类别 | 查什么 |
| --- | --- |
| 策划 | 规则、数值、状态流转、触发条件、边界情况；要用的配置表 / 数据表条目、开关、文案 |
| 后端 | 协议号是否存在、协议字段和策划要的数据是否对得上、有没有重复或占位协议 |
| 美术 | 预制体能否承接需求：缺节点、缺组件、结构和策划不符、缺 UI 图或特效 |
| 前端 | 显示逻辑是否说清：显示时机、优先级、层级、互斥、刷新时机、动效、空态和异常态 |

判不准时按阻断处理。阻断项的 `blockedReason` 以类别开头，例如 `后端：缺 10023 协议（奖励领取），需要协议文档和字段定义`，命令行会原样列出来。

### 4.4 策划案迭代：`bulings design`

适用：手里只有玩法灵感，还没有策划案。`mode` 必须是 `indie`。

```powershell
# 起第一轮：灵感可以是文件，也可以直接是一段文字（这时要给 --name）
bulings design --project <工程> --idea <灵感.md> [--name <策划案名>]
bulings design --project <工程> --idea "白天建造、夜里守塔" --name tower-defense

# 选选项推进一轮（可多选，逗号分隔）
bulings design --project <工程> --name tower-defense --decide G1
bulings design --project <工程> --name tower-defense --decide G2 --note "想再休闲一点"

# 只补充想法、不选选项，也推进一轮
bulings design --project <工程> --name tower-defense --note "剧情想轻一点"

# 定稿（要求四个维度都已确认；确实要放行加 --force）
bulings design --project <工程> --name tower-defense --finish

# 回看每轮的选项和选择（加 --json 输出机器可读结果）
bulings design --project <工程> --name tower-defense --history

# 只看进度和当前选项（不启动 Agent）
bulings design --project <工程> --name tower-defense
```

流程：每轮推进一个维度，顺序是 **玩法核心循环 → 剧情与世界观 → 美术风格与音频 → 游戏流程与关卡节奏 → 收尾**。每轮会给出 `indie.design.options` 个选项（默认 3 个），每个都写清代价；选完把结果写进策划案，再进入下一轮。

每轮结束后终端会打印当前选项和下一步命令，例如：

```
进度：第 2 轮（建议 4 轮） · 阶段 剧情与世界观 · 状态 iterating
维度：玩法已确认、剧情待定、风格待定、流程待定
本轮选项（用 --decide 选，逗号分隔可多选）：
  S1  无剧情，纯系统驱动
        没有角色和台词，靠关卡与数值变化推进
        代价：省一半内容量，但缺少记忆点，宣传不好讲
```

工作流会校验这一轮真的推进了：

| 校验 | 不满足时 |
| --- | --- |
| `round` 必须是上一轮 +1（第一轮是 1） | 退出 2，要求重跑这一轮 |
| 迭代中的一轮至少 2 个选项 | 退出 2 |
| `--decide` 的 id 必须存在于当前选项 | 退出 1，并列出可用 id |
| 带 `--decide` / `--note` 的那一轮必须在 `chosen` 里留下 `round` 记录 | 退出 2 |
| 选过的 id 必须记到本轮（不只是历史上记过） | 退出 2 |
| `--finish` 时 `status` 是 `done`、`options` 为空、四个维度都确认、正文非空 | 退出 2（`--force` 可跳过维度确认） |

另外两项是**警告不阻断**：本轮策划案正文没有变化（`design.json` 更新了、正文没更新）；已到建议轮次。每轮结束会把 `design.json` 快照到 `.bulings/design/<策划案名>/rounds/<轮次>.json`，`--history` 就是读这些快照。

选项 id 用阶段字母加序号：玩法 `G1`、剧情 `S1`、风格 `A1`、流程 `F1`。

产物：`.bulings/design/<策划案名>/design.json`（设计状态）、同目录 `brief.md`（灵感原文）、同目录 `rounds/`（每轮快照）、`Docs/AI/GameDesigns/<策划案名>.md`（策划案正文）。定稿后命令会提示接着跑 `bulings run --design`。

### 4.5 独游模式：`mode: indie`

```powershell
bulings run --project <工程> --design <策划案> [--name <功能名>] `
  [--no-dev-spec] [--no-feature-doc] [--no-framework] [--model <模型>]
```

命令和参数与工作模式一样，只有两点不同：**可以不给 `--prefab`**，**第一次跑会先建框架**。`--design` 一般就是 `bulings design` 定稿出来的那份策划案。流程：

1. **建立框架**（只在没有可用框架时）：选范式、落目录与程序集、把启动/事件/状态/配置/存档做成能跑的最小实现，写 `.bulings/indie/framework.json` 和 `Docs/AI/Frameworks/<工程目录名>.md`。这一阶段不写玩法功能。
2. **拆切片**：先做和工作模式同一套缺失分析（策划 / 后端 / 美术 / 前端，分阻断与非阻断），再按纵向切片拆任务，每项写 `framework` 挂载点（框架的系统 id 或扩展点名，新增写 `new: <说明>`）。挂载点不合法、或存在阻断性缺失时，都在写代码前停下。
3. **逐项实现**：一轮一项，优先复用扩展点，需要时往框架清单里追加登记。实现中发现的阻断性缺失同样标 `blocked` 停下。
4. **功能说明**：写清挂载的框架点、新增扩展点、下一个功能从哪接；非阻断缺失按四类汇总。

- 框架没写好（不存在、不合法、`status` 还是 `draft`）时退出码 `2`，不进入功能代码。补齐后 `resume` 继续。
- 框架阶段结束还会检查框架文档真的写出来了（`Docs/AI/Frameworks/<工程目录名>.md`），只是模板骨架也算没写；不想要求就把 `indie.framework.docEnabled` 设为 `false`。
- 已有可用框架时跳过框架阶段；`root` 和登记过的路径都会做漂移检查，找不到只打警告，扩展点为空或没覆盖四类也只打警告。
- 切片必须写 `slice`；`dependsOn` 指向不存在的 id、自依赖或成环，都会在写代码前退出 `2`。
- `--no-framework` 跳过框架阶段（适合已有自己架构的工程），切片仍要写 `new:`。
- 独游模式下 `split` 会拒绝执行；`kb` 可以照常用。
- 细节、`framework.json` 契约和常见问题见 [独游模式说明](独游模式说明.md)。

### 4.6 只读命令：`status` / `doctor` / `audit`

三个命令都不启动 Agent，随时可以跑。

```powershell
bulings status --project <工程> [--json]
bulings doctor --project <工程>
bulings audit --project <工程> [--json]
```

| 命令 | 看什么 | 退出码 |
| --- | --- | --- |
| `status` | 模式与工程名；所有策划案（轮次、是否定稿、维度确认数、正文路径）；框架（就绪与否、系统与 pending 数、扩展点数、漂移前 5 条、文档是否存在）；所有运行（阶段、任务完成数、阻断项 id 与原因）；下一步建议命令 | 总是 `0`（没有产物也能跑） |
| `doctor` | `[OK]/[WARN]/[FAIL]`：Unity 工程、`workflow.yaml`、当前模式的 Skill、`CURSOR_API_KEY`、Unity MCP 可达性（1 秒 TCP 探活）、独游模式的框架基线与文档、策划案目录可写 | 有 `FAIL` 时 `1` |
| `audit` | 用 `git status --untracked-files=all` 看工作区改动：命中 `protectedPaths`（错误级）、动了 `.meta`（警告级）、改动落在 `codeRoots` 之外（提示级）。不是 git 仓库时跳过 | 有错误级时 `1`，否则 `0` |

`status` 的 `--json` 和 `audit` 的 `--json` 输出同一份数据的机器可读版本，方便脚本消费。

另外，每个阶段（框架 / 分析 / 功能说明）结束后会自动跑一次审计，只把**错误级**问题打到 stderr（改到了 `protectedPaths`），不改变退出码——避免把工作区里本来就有的改动算成这次的问题。

### 4.7 继续与重试：`bulings resume`

```powershell
bulings resume --project <工程> --run <功能名> [--confirm-flow | --no-flow]
```

- 任务被阻塞：先补充信息或修正文档，再 `resume`。该任务会改回 `in_progress` 重做，原阻塞原因会带进提示。
- 中断留下的 `in_progress` 会重做那一项，不重做已完成的。
- 工作模式停在 `flow` 阶段：加 `--confirm-flow` 确认流程图后进入实现；`--no-flow` 跳过这张图。
- `--no-flow` / `--confirm-flow` 同时给时以 `--confirm-flow` 为准。

### 4.8 知识库：`bulings kb`

```powershell
bulings kb --project <工程> --action init
bulings kb --project <工程> --action update --name <功能名>
bulings kb --project <工程> --action check
```

| 动作 | 作用 |
| --- | --- |
| `init` | 读代码建立 `MAP.md`、`conventions.md`、`architecture.md`、`modules/*.md`；已有页面只补缺，不覆盖人工内容 |
| `update` | 按该功能的 `tasks.json` 只更新受影响的页面；没有要改的会明说“无需更新”。需要 `--name` |
| `check` | 只读核对，写 `CHECK.md`：过期、缺失、冲突、孤儿页 |

要点：

- 内容以代码为准；每条结论带代码路径；读不到证据的写进「待核实」。
- `init` 后建议人工审一遍地图、约定、架构和「待核实」。
- 建好后，`run` 会自动把地图交给 Agent，功能说明写完后也会提示它维护受影响的页面。
- `update` 和 `check` 需要先 `init`（`MAP.md` 必须存在）。

### 4.9 在 Cursor 对话里使用

用 Cursor 打开 Unity 工程。工作模式可以直接输入 `/BulingAI`（`/buling-ai` 相同）。一条消息里两种写法都可以，也可以混用：

```text
/BulingAI
--design <策划案> --prefab <预制体> --name <功能名>

/BulingAI
<策划案正文>
<预制体路径、@预制体，或预制体 YAML>
```

`--prefab` 可重复。只贴正文时写入 `docs/AI/Designs/<功能名>.md`（工程已有 `Docs/AI` 时跟已有目录）。当前对话按 `work-feature` 执行，不另起 `bulings run`。`mode: indie` 时改走 `indie-feature`。

也可以不打指令，直接说需求并给出路径。点名阶段或任务编号时只做那一段：

- “只做分析” / “只写开发说明”
- “只实现 T3” / “只重做 T3”
- “只写功能说明”
- “用 client-split 把 `<策划案>` 的客户端部分分离出来”
- “用 knowledge-base 检查知识库”
- “用 indie-design 从 `灵感.md` 开始迭代策划案，按玩法、剧情、风格、流程各给我几个选项”
- “用 indie-feature 建框架” / “只实现 T3 这个切片”

没点名阶段时，按顺序自己做完，一次一项任务。策划案迭代在对话里也一样：Agent 把选项列出来，你选完它再写下一轮。

**对话入口和命令行的差别**：

| | 命令行 | Cursor 对话 |
| --- | --- | --- |
| 起 Agent | `bulings run` / `design` 在本机拉起 Cursor SDK Agent，需要 `CURSOR_API_KEY` | 当前对话的 Agent 自己做，不需要 key |
| 轮次/选项校验 | 由 Python 强制（轮次 +1、至少 2 个选项、选项 id 存在、选择写进 `chosen`） | 靠 Skill 里的自检清单，没有强制 |
| 产物位置 | 一样 | 一样 |

两边交错使用没有问题：命令行会按同一套规则检查对话里已经写下的 `design.json`，不合法就当场停下。Cursor 没自动加载 Skill 时，直接把 `.cursor/skills/<名字>/SKILL.md` 路径告诉它。升级本仓库后要重新 `bulings init`，否则工程里还是旧 Skill。

### 4.10 使用 Unity MCP 时的行为

配置好且连得上时，Agent 可以：读场景/预制体层级与序列化字段、刷新编译并读控制台、在编辑器里绑定预制体引用、运行测试。

边界：

- 分析阶段只读。
- 实现阶段只动当前任务涉及的对象。
- 不改 `protectedPaths` 和 `.meta` 的 guid；不通过 MCP 删资源（任务明确要求除外）、不触发批处理构建。
- 任务完成前要求控制台无编译错误；涉及绑定的完成标准用 MCP 回读确认。
- 连不上时必须如实说明，验证不到的写进开发说明，不能标成已验证。

### 4.11 交付流（长任务）

跨多轮、需要独立评审和最终验证的功能，用 `bulings delivery ...` 与 delivery Skill。它只在用户明确要求时使用，细节见 [交付任务文档](delivery-tasks/00-索引与共同约定.md)。局部小改不要走它。

### 4.12 命令与退出码速查

| 命令 | 必填参数 |
| --- | --- |
| `init` | `--project` |
| `design` | `--project` + `--idea` / `--decide` / `--note` / `--finish` / `--history` / `--name` 之一（仅 `mode: indie`） |
| `split` | `--project` `--design` |
| `run` | `--project` `--design`；`--prefab` 至少一个（`mode: work`），独游模式可省 |
| `resume` | `--project` `--run`；`--confirm-flow` / `--no-flow` |
| `status` | `--project` |
| `doctor` | `--project` |
| `audit` | `--project` |
| `kb` | `--project` `--action`（`update` 还需 `--name`） |

退出码：`0` 完成；`1` 没启动（参数、配置、密钥、启动失败、选项 id 不存在；独游模式下 `split` 也走这个码；`doctor` 有 `FAIL`；`audit` 有错误级问题）；`2` 已启动但没做完（失败/取消、任务阻塞、分析阶段有阻断性缺失、工作模式流程图没确认、`tasks.json` / `framework.json` / `design.json` 不合法、框架文档没写、切片或依赖写错、轮次没推进、没写出预期文件）。

## 六、常见问题

| 现象 | 处理 |
| --- | --- |
| 不是 Unity 工程 | `--project` 要指向含 `Assets`、`ProjectSettings` 的目录 |
| 提示还没有 Skill | 先执行 `bulings init` |
| 缺少 `CURSOR_API_KEY` | 设置环境变量后重开终端 |
| 提示已有未完成的运行 | 用 `resume` 继续，或确认后处理旧的 `state.json` |
| 任务一直 blocked | 看 `tasks.json` 的 `blockedReason`：开头就是类别（策划 / 后端 / 美术 / 前端）。按那条补齐缺失的规则、协议、预制体节点或显示逻辑，再 `resume`；补齐前命令会一直停在分析阶段 |
| 功能说明里有一堆「未补齐的非阻断项」 | 这是预期的：缺失分析里判为非阻断的项会先用保守做法实现，流程结束时按四类汇总。要补的时候按清单一条条给资料，再单独提任务 |
| `split` 退出码 2 | Agent 没写出文档，看输出后重跑 |
| `design` 提示选项 id 不在这一轮 | 报错里有可用 id；先不带参数跑一次 `design` 看当前选项，再 `--decide` |
| `design` 退出码 2 说轮次没推进 | Agent 没把 `round` 写成上一轮 +1，重跑这一轮；正文改完还不行就手动补 `design.json` |
| `design` 定稿时提示 status 不是 done | 让 Agent 重跑 `--finish`；或把 `design.json` 的 `status`、`stage` 改成 `done` 并清空 `options` |
| `design` 提示「没有记进 chosen」 | 带 `--decide` / `--note` 的那一轮要在 `chosen` 里留一条 `{round: 本轮, ids: [...], note}`；让 Agent 重跑这一轮，或手补 `design.json` |
| `design` 定稿提示维度没确认 | 把没确认的维度写厚并标 `confirmed: true`；确实要放行加 `--force` |
| `design` 警告「正文没更新」 | `design.json` 更新了但策划案正文没动。让 Agent 把这一轮的内容写进正文；警告不阻断，但下一轮会接着用旧正文 |
| 灵感改了想重来 | 换一个 `--name` 重新 `--idea`；已有策划案时 `--idea` 会被拒绝，避免覆盖 |
| 独游模式提示框架不合法或还是 draft | 补 `framework.json` 并把 `status` 改成 `done`，再 `resume`；或加 `--no-framework` |
| 提示框架文档没写出来 | 把 `Docs/AI/Frameworks/<工程目录名>.md` 按 `framework-template.md` 写出来；或设 `indie.framework.docEnabled: false` |
| `framework.json` 解析失败说路径不对 | 所有路径必须是相对工程根的（不能 `C:/...` 或 `/...`），`root` 也一样 |
| 提示切片没有挂在框架上 | 按报错里列的挂载点改 `framework`；要新增就写 `new: <说明>` |
| 提示任务没有写 slice | 独游模式每项任务都要有纵向切片名；补上 `slice` 再重跑分析 |
| 提示依赖不存在或成环 | 改 `dependsOn`：只能指向本 `tasks.json` 里已有的任务，不能自依赖、不能互相依赖 |
| 不知道现在到哪一步了 | 跑 `bulings status --project <工程>`：策划案、框架、所有运行和下一步都在一屏里 |
| 工作模式卡在 `flow` 阶段 | 看 `.bulings/runs/<功能名>/flow.md`：页面交互和数据流没问题就 `resume --confirm-flow`；不想看就 `resume --no-flow` |
| `--confirm-flow` 说流程图不能确认 | 按报错补：要有 mermaid 图、「页面与入口」「数据流向」两节，且不是空壳；补完再确认 |
| 代码里出现了 `transform.Find` / `GameObject.Find` | 这是不该有的兜底。让 Agent 改成预制体内绑定；实在绑不了，让它把预制体列进「预制体绑定 → 待用户补绑定」 |
| 怀疑环境有问题 | 跑 `bulings doctor --project <工程>`：工程、配置、Skill、密钥、MCP、框架逐项打 `[OK]/[WARN]/[FAIL]` |
| 改过 `mode` 后 `resume` 报错 | 一次运行绑定建立时的模式，改回去或另开一次运行 |
| `kb` 提示未启用 | `knowledge.enabled` 为 `false` |
| `kb update/check` 提示没有 MAP.md | 先 `kb --action init` |
| Agent 没用 MCP | 检查 `.cursor/mcp.json` 条目、Unity 里服务是否运行、地址是否正确 |
| 修改了 MCP 配置没生效 | 已有同名条目不会被 `init` 覆盖，直接改 `.cursor/mcp.json`，改完重启 Cursor |
| `init` 后 `mcp.json` 还是没有条目 | 看三个可能：`unity.mcp.enabled` 是 false、`command` 和 `url` 都空、文件里有同名 `server` 条目 |
| MCP 配了但 Agent 说连不上 | 工作流只写连接信息；去 Unity 里确认插件在跑、端口对得上，然后让 Agent 重新试一次 |
| 新文件出现在 `git status` | 检查 `.git/info/exclude`；已被跟踪的文件排除规则无效 |

## 七、注意事项

- 生成的代码和文档请自行审阅后再提交；工作流不会替你 commit。
- 知识库和代码冲突时以代码为准。
- 升级工作流后记得重新 `init`，否则工程里的 Skill 还是旧版本。
- 新增的 `split`、`kb`、`design` 与独游模式目前只有配置、提示拼装和假 Agent 驱动的测试，尚未用真实 Agent 端到端验证，首次使用请先在小功能上试跑。
